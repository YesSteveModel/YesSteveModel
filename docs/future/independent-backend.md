# 独立 Backend

独立 Backend 尚未实现。目前代码里只有权威模式选择和部分传输抽象；入站处理、握手、玩家状态同步以及大部分控制逻辑仍绑定在 Forge 编排上，尚未抽离。

## 目标边界

Backend 可以成为当前游戏连接的唯一远端玩家状态权威，但绝不能和游戏服务端并存、共同决定状态。状态权威与[外部模型源](external-model-sources.md)是正交的：Backend 可以只同步玩家状态，也可以另行提供模型目录与资产；成为状态权威不会自动让它变成模型源。

Backend 应复用当前协议中仍适用的玩家状态与控制语义，并为其定义独立的传输绑定；不得恢复已经删除的资产分片协议，也不得依赖 Forge、Minecraft 连接对象、JNI 或客户端的 native 库来实现。

会话权威的选择规则保持不变：`AUTO` 依次尝试 Game Server、Backend、Local Only；`BACKEND` 只尝试连接 Backend；`LOCAL_ONLY` 禁止任何远端权威。权威只在连接建立阶段选定，同一条连接内不允许热切换。

## 最小接入条件

1. **认证连接**：连接的建立、关闭、超时和重连都有独立的身份与代际标记（generation），凭据严格绑定到对应的传输对端。
2. **双向传输**：覆盖发送、入站分发、断连通知、背压控制以及明确的发送完成信号。
3. **握手编排**：协商协议版本、特性集、资源限制与状态策略，双方校验通过后原子激活会话。
4. **单一权威**：区分用户偏好策略与当前生效权威，拒绝来自旧连接的结果，并禁止跨权威热切换。
5. **主体映射**：写入主体身份必须来自已认证的对端；player ID 只用于路由，不能替代身份认证。
6. **与宿主解耦的入口和生命周期**：抽离 Forge 回调，确保取消、错误、迟到结果和断连都能彻底清理会话占用的全部资源。

如果 Backend 同时承担模型分发，还必须补齐目录修订与重同步、权限与凭据校验、资产传输背压与取消，以及目录发布与会话的原子绑定，不能向客户端发布无法下载的悬空目录项。

## 实施顺序

1. 补齐与具体传输层解耦的入站、断连、握手与会话编排；
2. 完成带身份认证的状态权威及旧连接隔离；
3. 再单独接入模型目录与资产分发，不与外部模型源混在同一轮交付；
4. 通过协议一致性测试、恶意输入测试、取消、重连和多人联机验证后，再标记为当前支持能力。
