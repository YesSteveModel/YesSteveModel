# 产品决策维护规则

文档按独立判断分别归层，不把一整段决策原文原封不动归档到同一层。本目录树只保留产品承诺、产品理由和必要边界；实现机制与工程理由下沉到架构文档，格式与协议细节进入标准文档，当前支持状态和验证结论则由状态文档维护。这里的“自包含”要求读者仅凭本层就能完整判断产品义务，不必把全部技术推导留在产品决策中。

“可观察”不等于“已承诺”。替换内部机制后，只要仍满足承诺的结果、领域语义和外部契约，就不应修改产品决策；如果产品确实对某种机制本身提出了约束，则保留该约束，具体的实现方式依然下沉。单纯的分层整理和归并必须保持原有产品含义。一旦需要改变既有承诺，或下游文档与本目录树发生冲突，须由维护者提交产品负责人决定，不能以当前实现或“技术细节”为由自行改写。

只有出现独立的产品选择时才新增 DD；补充契约或例外归入已有 DD，表达同一选择的重复 DD 应当合并。合并时必须保留原有的独立契约、理由、优先级、例外与互斥条件，主题相近不足以构成合并理由。下沉机制时连同工程理由一并移走；冗余节点必须等其独有含义被完整承接后才能删除。保留存续判断的 ID，但不为了留住某个 ID 而维持重复定义。

每次修改须完成以下影响检查与同步：

1. 修改前收集涉及的旧 ID、新 ID 和包路径；如果改动涉及包头、公共规则或例外，还须把受其限定的全部节点纳入范围。用 `rg` 精确检索本目录树及下游文档中的相关 ID、包路径与名称。
2. 通读命中节点所在的完整决策边界，逐项检查嵌套 BC、显式 Decision 归属、Constraints、条件 Needs、Requirement 以及 Select 与 Uses。区分纯导航变化与语义变化，并沿受影响的依赖继续排查，直到没有未处理的适用依赖；正文未变并不代表不受影响。
3. 更新唯一正文、下游引用以及 Landing 和反向索引，对照最终 diff 复核改动范围，最后再次搜索已退役的 ID 和旧路径。工具检索只能给出候选，未在索引中登记的依赖仍须按语义人工判断；不另建长期影响台账。

已决定下沉的规则及其例外，必须在架构或标准文档中具备明确落点。移走实现机制后，仍承载产品含义的节点保留 ID，不再有产品含义的节点退出本目录树。下游改为引用规则的新落点，复杂度地图同步复核根依据；不为了维持旧路由而保留空节点。

从仓库根目录运行：

```sh
python docs/tools/check_docs.py
git diff --check
```

修改 Mermaid 图表时须另做渲染校验。自动化校验用于检查 ID 唯一、引用有效、BC 归属、因果关系无环、需求状态与缺口一致，以及 Landing 与反向索引是否对应；条件 Needs 和导航允许成环。

结构校验无法证明分层、归并或影响范围是否完整。语义复核须确认每项承诺都有产品依据，理由与例外保持自包含，归并没有丢失原有义务，实现机制没有被误升格为产品承诺，且当前实现、未来方向与验证状态彼此没有混淆。本页维护规则随文档约定同步更新；规则属于文档治理，不创建 DD 或 BC。决策完备不代表生产实现已完成或运行时验收已通过。
