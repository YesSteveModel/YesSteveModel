# 文档治理规则

本页适用于整棵文档树。各目录的职责与权威边界见[文档入口](README.md)；架构文档另遵循[架构文档维护](architecture/documentation-rules.md)。

## 信息取舍与维护

文档应写得清晰克制，既不展开冗余说明，也不堆砌缺乏独立信息量的防御性免责语句。能从已有定义自然推导出来的结论不必重复；如果为了局部阅读顺畅或跨主题汇总确实需要复述，应链接到唯一权威正文，不要另写一套定义。不过，必要的适用条件、例外情况以及不直观的限制必须明确保留。

不同层次的文档各司其职：文档重点保留结论、适用条件、例外以及不显然的理由、代价与限制。其中，产品层记录对外承诺和领域语义；可替换的技术机制与工程权衡归架构层；设计与实现文档的划分以及实现细节的收录标准见[架构文档维护](architecture/documentation-rules.md)。注意，代码当前表现出的参数或行为不会自动成为产品承诺。

编码任务一旦改变决策、设计、架构或运行机制，应同步更新受影响的文档：

- 先修改唯一权威正文，再沿着依赖和引用链复核相关的摘要页、派生视图与验证说明；涉及产品决策时，按[产品维护规则](product-decisions/maintenance.md)复核受影响的决策和下游文档。
- 删除重复或失效内容前，先确认其中仍然有效的条件与约束已有明确位置承接；已经失效或冗余的内容直接删除即可，不必为了留档转存到其他页面。
- 只要原有依据和前提没有变化，可以直接沿用已有结论和验证证据，不必重复论证。

文档只描述当前有效的结论，不记录讨论和纠错沿革、临时计划或已废弃的中间方案；如果过去踩坑得到的经验仍然制约当前选择，可以只保留对应的约束和适用边界。旧版实现仅用于理解历史背景，不能用来定义当前系统的行为。此外，文档本身和自动化文档检查都不能替代当前源码与运行验证，也不能证明未被覆盖的行为或性能；未经实测验证的性能动机不能直接写成性能收益。

## 写作约定

- 统一使用相对链接；正式文档应自包含，不依赖已弃用资料。
- 组件按职责命名，不要用本机工程目录名代指项目或架构角色；不记录仅对单次本地检出、本地构建或核查有意义的路径、分支、提交记录和时间。
- 稳定的类型或方法名可以作为责任或契约的定位锚点，但不要附带源码路径、行号或成员清单，也不要展开与边界契约无关的调用步骤。
- Minecraft 和 Forge 相关的概念优先使用正式符号。YSM 原创、且无法从通用术语直接推知的稳定名称，统一在[术语表](glossary.md)中给出释义；局部符号和已在标准文档中定义的术语不必重复收录。
- 格式、缓存或协议尚未冻结时必须明确标出；未来计划、历史背景、已知问题与已实现能力应分开表述，避免混为一谈。

## 文档检查

在仓库根目录运行 `python docs/tools/check_docs.py`。该脚本负责校验相对链接、标题锚点、页面可达性、目录分层与复杂度关系，但不保证语义完整或生产行为正确。修改检查脚本时应同步运行其测试；修改 Mermaid 图表时需另做渲染校验。
