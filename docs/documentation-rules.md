# 文档治理规则

本页适用于整棵文档树。目录分工见[文档入口](README.md)；架构树分层规则见[架构文档维护](architecture/documentation-rules.md)。

## 信息取舍与维护

文档只记录当前有效的结论、适用条件、例外与不显然的工程取舍：

- **单一权威源**：产品对外承诺归 `product-decisions/`，公开格式与协议归 `standards/`，可演进的模块设计与实现映射归 `architecture/`。跨页引用时直接链接权威源，不另写第二套定义。
- **不复述通识与源码**：能由类型签名、通用工程常识或上游规范直接推知的规则不必重写；代码当前行为不会自动成为产品承诺。
- **区分两类语气**：外部硬约束（产品承诺、已冻结标准、宿主线程与内存安全底线）直接写明条件与后果；当前内部实现前提用中性事实语气描述“现在怎么运作、若重构打破需同步改什么”。
- **只记现状**：不记录讨论与纠错历史、临时计划或已废弃方案；单次实验跑分、提交哈希与时间戳不写入长期文档。未落地差异归 `status/`，未选定方案归 `future/`。
- **变更同步**：修改设计、契约或运行机制时，先改唯一权威正文，再更新直接依赖的摘要、派生视图与验证入口；失效或冗余内容直接删除，前提未变时直接沿用已有结论。

## 写作约定

- 统一使用相对链接；正式文档保持自包含，不依赖已弃用资料。
- 组件按职责命名，不使用本机目录别名代指项目或角色，不写入本机路径、分支、提交记录或时间元数据。
- 稳定类型或方法名可作为定位锚点，但不写源码行号、全量成员清单或无关调用步骤。
- Minecraft/Forge 概念使用正式符号；YSM 专有术语统一在[术语表](glossary.md)定义。
- 尚未冻结的格式、缓存或协议需显式标明。

## 文档检查

在仓库根目录运行 `python docs/tools/check_docs.py`，校验相对链接、标题锚点、页面可达性、架构结构与源码 Javadoc 文档链接。修改校验脚本时同步运行其单元测试；修改 Mermaid 图时另行校验渲染语法。
