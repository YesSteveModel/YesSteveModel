# 文档治理规则

本页适用于整棵文档树。事实来源与权威边界见[文档入口](README.md)；架构文档另遵循[架构文档维护](architecture/documentation-rules.md)。

## 信息取舍与维护

表述言简意赅，避免过度展开和无独立信息价值的防御性表述。不重复记录能从已有信息轻松且稳定推导出的结论；为局部理解或跨主题归纳，可保留必要冗余，并链接唯一权威正文，不另立定义。必要的适用条件、例外和非显然限制仍须保留。

保留结论、适用条件、例外及非显然的理由、代价与限制。产品层保留承诺和领域语义；可替换机制及工程理由归架构。设计到实现的划分与实现细节准入见[架构文档维护](architecture/documentation-rules.md)。可观察的参数或行为不自动成为产品承诺。

编码任务改变决策、设计、架构或机制时，应同步更新受影响文档。变更时更新唯一正文，沿受影响的依赖和引用复核摘要、投影及证据；涉及产品决策时，按[产品维护规则](product-decisions/maintenance.md)复核受影响的决策与下游。承接仍有效的条件与义务，再删除重复或失效内容；不要求将所有删除内容转存其他页面。已有依据和前提未变时，可继承已有结论和证据。

文档保留当前结论，不记录纠错沿革、临时计划或已失效的中间方案。仍约束当前选择的经验可保留其约束和适用边界。旧版实现只用于理解历史，不能定义当前系统。文档和检查结果不能替代当前实现与运行验证，也不能证明未覆盖的行为或性能；未经验证的性能动机不能写成收益。

## 写作约定

- 用相对链接；正式文档应自包含，不依赖已弃用资料。
- 组件按职责命名，不以本机工程目录名代指项目或架构角色。不记录仅对本地检出、构建或核查有意义的路径、分支、提交和时间。
- 稳定符号可作为责任或契约的定位锚点；不附源码路径、行号或成员清单，不展开不承重的调用步骤。
- Minecraft 和 Forge 优先使用正式符号。YSM 原创且不能由通用术语推知的稳定名称在[术语表](glossary.md)释义；局部符号和标准已定义的术语不重复收录。
- 明确格式、缓存或协议的不稳定状态；计划、历史、已知问题与已实现能力分开表述。

## 文档检查

从仓库根目录运行 `python docs/tools/check_docs.py`。该入口检查链接、锚点、可达性、目录分层和复杂度关系，不证明语义完整或生产行为正确。修改检查器时执行其测试；修改 Mermaid 时另做渲染校验。
