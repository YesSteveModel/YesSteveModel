# 玩家偏好与周期提交

上级契约：[模型存储](overview.md#seam-contract)。本页定义独立存储能力；玩家输入资格与恢复后的游戏效果归会话 owner。

## 职责与边界

`PlayerPreferences` 提供客户端玩家偏好的读写与跨版本首次继承，并持有全进程唯一的 `StorageWriteBuffer`。该缓冲区把 roaming 状态、本地模型选择（Local selection）、收藏、清除（clear）、首次填充以及远端资源使用事件排入同一条逻辑序列，并借用存储区域的[数据库执行域](overview.md#数据库执行)异步落盘，不另选根目录，也不直接操控私有 SQLite 连接。

偏好数据由玩家 UUID、发布身份与事实种类共同定位：
- **Roaming 状态**：以 `UUID + 发布身份` 为键，明确空值也属于已存在的记录；必需默认模型（intrinsic）与同源普通默认模型的 roaming 分开存取。
- **收藏**：只接受普通 `ModelId`。
- **Local selection**：按玩家 UUID 保存完整发布身份与纹理意图；记录缺失不代表显式选择了 intrinsic。

本模块不负责核验玩家权限、模型可用性或远端内容交付状态——调用方应自行确立这些前提，并在接纳异步结果时复核自身权威。存储成功既不主动回写运行时状态，也不发送网络消息。

### 偏好读写与首次继承

**边界与权威**

Java 负责校验业务值、检查字段布局以及选择继承来源（donor）；native 负责按完整键执行查询、整值写入事务与原子首次填充。玩家偏好属于主数据，不能从任何缓存索引重建。

**前置条件与输入**

区域 owner 提供已经固定的 `DATA` 根目录与数据库执行域；`PlayerPreferences` 懒创建并持有 `PlayerData` 能力，数据库文件名与 schema 保持私有。每次操作都捕获玩家 UUID、发布身份和独立快照；恢复调用还会传入目标模型的不可变合法字段集合。

SQLite 中的 roaming 保持命名数组格式 1；偏好 scope 与写队列使用宿主的 `NamedRoamingSnapshot`，按字段名保留数值。引擎局部编号只在明确配对的布局上下文中解释，调用方在恢复新安装时负责把字段名映射为局部编号。

Roaming 载荷受以下格式约束：最多包含 64 个唯一字段，字段名非空且不超过 32 个 UTF-8 字节，字段值为有限 `F32`。存储入口整份校验数组长度、字段名与数值，持久化读取和首次继承还会额外核对目标布局；一旦持久记录中存在未知字段，恢复立即失败并保留原记录不动。写入方必须先确立当前布局与生产者资格，再交出稳定只读的名称数组与值数组；门面校验边界后直接持有这些数组，后续若有一方需要修改数组，必须先自行复制。

**结果与保证**

返回结果明确区分 `Missing`、完整值、已提交、失败与取消。普通更新只替换单个完整键，不影响其他 UUID、发布角色或事实种类。收藏分页结果会同时包含已取消收藏的成员以推进 keyset 游标，调用方一直读到空页才算遍历结束。

首次继承只在目标键为 `Missing` 时触发：
- 仅版本化的命名模型参与继承：在同 UUID、同 family 且版本号严格更低的记录中挑选 donor，先按 SemVer 优先级比较，再取完整版本字符串 ASCII 序最大者。分页检索逐页观察，不锁住 donor，也不强求看到最新完整集合。
- 明确空记录可以作为 donor；未版本化身份、`hash:` 身份与 intrinsic 不参与继承。找不到 donor 时，为目标建立一条明确空记录。
- Java 只校验最终选中的最高版本 donor：如果该 donor 数据非法或与目标布局不兼容，整次恢复直接失败，绝不继续降级尝试更老的版本。
- Native 在单个短事务内执行“若目标缺失则插入，若已被并发写入则直接返回已有记录”，随后由 Java 复核返回值。整个过程不修改原 donor 记录或收藏。

**所有权与时序**

所有线程都向同一条 FIFO 入口提交不可变操作：

- **逻辑接纳与内存覆盖**：入口返回 `QUEUED` 只表示拿到了队列容量配额；直到主线程 `tick` 消费入口并确定逻辑顺序后，副作用操作的 `Operation.admission()` 才变为 `ACCEPTED`。主线程按完整键维护最新的整值内存覆盖层；读取操作在自己的接纳点固定观察视图，只有内存覆盖层没有记录时才下沉查询数据库。旧操作完成后，只能撤掉它自己仍代表的那份覆盖；分页读取在页与页之间不承诺一致性快照。
- **查询与副作用句柄**：纯读取返回 `StorageQuery`，排队项仅弱持有该句柄；worker 执行前先提升为强引用，若调用方已关闭或丢弃句柄则直接跳过读取。Worker 直接发布独立不可变结果，结果发布与 `close` 共用同一个同步点；关闭句柄不会撤销调用方已经取出的快照。查询操作的容量配额归还不依赖消费者再次轮询，已进入 JNI 的操作则在 JNI 实际结束后归还容量。写入、clear、首次填充与 flush 返回带强 owner 的 `StorageWriteBuffer.Operation`，调用方通过 `result()` 观察落盘结果（仅代表存储层效果，不证明运行时安装或断电持久性）。`restoreRoaming` 在开始执行前可以取消，一旦开始则继续完成原 UUID 与身份的落盘。
- **客户端接线**：主动选择由 `ClientDemandCoordinator` 准备好完整声明、初值与持久资格，在本地提交边界移交给新 scope，不等待服务端回显。`PlayerPreferenceSession` 管理自身 scope 的恢复；业务 owner 切换时先撤销旧结果的采用资格，再关闭查询句柄或取消未开始的恢复。Local selection、收藏与本地 roaming 恢复均在客户端主线程 tick 中采用，动画和渲染线程不轮询查询句柄。
- **启动预热**：[启动预热](../../runtime/overview.md#启动模型一次性预热)在显式 `LOCAL` 模式且尚未进入世界时，直接以当前账户 UUID 调用 `readSelection`，复用同一套逻辑读取顺序与完整 selection 解析。它只消费查询结果，玩家进入世界后的实体绑定与偏好恢复仍由玩家生命周期负责。

**失败与拒收**

普通写入在入口校验完结构并建立逻辑覆盖后，后台 worker 仍会读取并校验磁盘上的原记录：如果原记录无法解析或读取失败，则阻止持久覆盖（但内存中的逻辑覆盖仍可见）；对于布局不兼容的合法记录，仍允许通过显式 clear 清除。所有存储结果都保留原始失败信息，绝不伪装成 `Missing`、空值或保存成功，也不会盲目覆盖原数据库。

客户端查询失败按场景执行临时降级：
- **Roaming 查询失败**：无论本地还是联机主动选择初值，调用方都以临时空值继续，同时把该 scope 标为“不可持久化”。合法变化仍参与运行期求值与网络上报，但整段 scope 期间不向磁盘提交 roaming 快照，直到切换模型后重新查询；同 scope 内换纹理或重装不会恢复持久资格。用户显式执行 clear 会用明确空值替换该 scope 并独立尝试持久清除，此后新 scope 的真实变化可以恢复持久化。
- **收藏与选择查询失败**：收藏分页中任一页失败，本次内存收藏集整体降级为空。Local selection 查询失败时临时采用普通 `builtin:default`，不把该回退写回磁盘。
- **日志与清理**：上述查询失败只记录 DEBUG 日志，仅在 `DebugAnimationScreen.isEnabled()` 开启时于聊天栏提醒。写入失败仍按原策略处理；已取消或失效的旧结果只做收尾，不触发降级逻辑。

对当前生效选择执行 clear 时，客户端在本地提交边界先退休旧生产者、建立明确空 scope，再在发包前向共享 FIFO 入口提交清除。清除操作在入口被接纳后立即写入明确空覆盖并截断写入归并窗口：排在前面的已执行项先完成落盘，后续新写入排在 clear 之后。如果入口拒收 clear，则不建立空覆盖；如果后续落盘失败，也不撤销已经接纳的内存空覆盖。调用方另行汇报运行时清除与重新选择的结果。

**证据与依赖**

本契约依赖[数据库执行](overview.md#数据库执行)与[固定区域](overview.md#固定区域与目录观察)。`PlayerPreferencesTest` 覆盖 donor 选择向量、非法值、布局校验与发布角色；`SharedStorageProcessTest` 通过独立 JVM 验证多进程共享库与首次填充并发竞争；游戏内生产者、恢复窗口与网络重选由会话组合测试验证。

### 周期提交与关闭

**边界与权威**

主线程是逻辑顺序与内存覆盖层的唯一写入者。Roaming 按“固定区域 + UUID + 发布身份”保留整份快照，Local selection 与收藏按各自完整键保留，远端使用事件（usage）按“固定 remote 能力 + `ContainerId`”保留最大事件 UTC 秒级时间戳。其他线程只负责向 FIFO 提交操作，绝不直接修改覆盖层。

**前置条件与输入**

客户端由 `ClientModelService.tick` 驱动推进，专用服务端由服务端 tick 驱动推进。批次计时使用单调纳秒时钟；usage 事件的 UTC 秒取自事件发生时刻向下取整，不取落盘提交时刻。关闭动作沿 owner 的排他生命周期窗口执行。

**结果与保证**

批次形成、容量配额与归并规则如下：
- **定时成批与截断**：自首批待提交项进入起满 1 秒后打包成批，期间持续涌入的新写入不重置计时器；遇到读取、clear、restore 或显式 flush 时会提前截断批次。
- **有界容量**：单批最多 64 项且不超过 1 MiB；入口队列、内存覆盖层、观察切片与在途操作合计最多 256 项且不超过 1 MiB。容量饱和时入口直接返回 `FULL`，不留下半套覆盖。这一内存容量不限制磁盘上存储的偏好总量。
- **写入归并**：针对同一个键、中间没有穿插观察操作的连续写入会归并为最后一份整值，被覆盖的旧操作报告 `SUPERSEDED`，不声称已落盘。读取、clear、restore 与 flush 均会截断归并窗口。
- **独立事务**：后台 worker 逐条调用既有业务 JNI 执行批内保留项，每一项仍保持独立事务，因此同一批次允许部分成功。Native 更新 usage 时取原记录与新事件的最大值，UTC 时钟回拨不会导致记录倒退。

**所有权与时序**

已经逻辑接纳的最新内存覆盖，即使落盘失败或返回提交状态未知（unknown），在内存中仍继续可见。普通 tick 不会自动重试失败项；后续针对同一键的新合法整值可以更新内存覆盖，但不会改写旧操作的结果。

显式调用 `flush` 时，会在接纳点截取当前操作前缀，只针对当时“已失败、确定未提交且仍是最新覆盖”的条目安排一次重试；当前仍在途的操作如果随后失败，不会由这次 flush 重试，unknown 以及已提交后的清理失败也绝不重放。`Operation.report()` 如实保留前缀内各项的独立结果，后续新写入不计入本次 flush 承诺。

同一键的新写入不能抵消历史上的 unknown 状态：存储 owner 会把 unknown 和独立副作用失败一直保留到关闭报告，并继续计入缓冲区容量。`flush` 也会一并追踪前缀内虽已被新值覆盖但仍在途的旧写入——如果那笔旧写入最终成为 unknown，flush 仍必须报告存在未解决状态；相比之下，已知的历史失败可以被前缀内已确认落盘的新值抵消。

受控域显式关闭时，先停止所有生产者，再调用 `closeAndDrain`：先封口入口并结束尚未逻辑接纳的排队项，接着排空已经接纳的批次与 flush（未尝试过的条目获得一次正常落盘机会，已失败条目不自动重试）。专用的 drain 流程不依赖普通 tick 或消费者回调，结束后生成包含关闭窗口内各操作结果与未保存事实的关闭报告，最后由区域 owner 关闭数据库执行域与 native 资源。

[JVM 进程退出](../../runtime/overview.md#jvm-进程退出)不触发 `flush` 或 `closeAndDrain`。正常退出进程也允许丢失入口、覆盖层、排队及在途操作中尚未落盘的近期状态——操作被逻辑接纳或内存可见，不承诺进程退出时一定已写盘。但落盘的每一条数据依然受整份校验与独立原子事务保护，进程退出不放宽这些校验条件；显式 flush 的前缀语义和受控域关闭能力照常保留。

**失败与拒收**

提交入口明确返回 `QUEUED`、`FULL` 或 `CLOSED`，副作用操作在主线程接纳后另报告 `ACCEPTED`。落盘失败既不撤回已经生效的内存值，也不改写玩家、模型或网络状态。Usage 时间戳只记录交付历史，不证明内容依然有效、已无消费者或可以清理，本模块不执行 remote 缓存清理。

**证据与依赖**

本契约依赖[偏好读写](#偏好读写与首次继承)与[数据库执行](overview.md#数据库执行)。`StorageWriteBufferTest` 通过受控推进的虚拟时钟与真实 SQLite 故障，验证排序、观察边界、max 归并、失败覆盖、显式 flush、弱引用查询和关闭行为；内容交付事件与游戏 tick 的实际接线由对应 owner 验证。

## 设计取舍

把 donor 分页筛选留在 Java 侧、把原子首次填充放在 native 短事务内，避免了跨语言重复实现 SemVer 比较逻辑，也避免了在业务校验期间长时间占用 SQLite 写事务。接受进程直接退出时丢失尚未落盘的近期状态，省去了退出排空钩子、持久写前队列、跨库事务、跨实例广播和强制刷盘带来的复杂度。

用同一个写缓冲统一调度玩家偏好与 remote 使用事件，可以有效控制总在途请求量；各库和各键分别在独立事务中完成则降低了失败耦合，代价是整批没有统一的原子提交点，调用方必须逐项消费反馈。
