# 架构文档维护

本页定义架构文档的专用规则，通用要求见[文档治理规则](../documentation-rules.md)。若涉及产品语义变更或冲突，按[产品维护规则](../product-decisions/maintenance.md)仲裁；单纯整理文档不改变生产契约。

## 组织与递归展开

`architecture/README.md` 是唯一的系统总入口，负责呈现核心数据流和按问题导航。有独立目录的子系统用 `overview.md` 承载核心设计；单页子系统直接按职责命名文件，不必为契约单独建目录。设计专题与入口同级存放，实现映射按需放入 `implementation/`。子系统内不设 `design/` 目录、同级 `README.md` 或实现总览，也不强求设计页与实现页一一对称。

每一层设计页都应能独立说明本级的输入、输出、责任边界、发布条件、失败后果与结束义务。下级可以细化节点、交接或生命周期，但把下级折叠后，本级契约仍应自洽成立。父级只定义跨模块组合规则，下级定义局部接口，父级不重复搬运下级的全部接口、状态和例外。跨分支规则归实际负责组合的一方，不按目录树机械上移到最近公共目录。

子系统按职责划分，不按目录或页面形态划分，递归拆分不限深度。值得独立拆分的子系统应具备明确的职责与输出、独立的状态或资源责任、清晰的交接与失败边界，以及局部阅读价值。不能仅凭线程、package、类结构、篇幅或目录对称来切分边界。如果某个页面只剩重复摘要或符号清单，就应合并；交接专题也不自动成为子系统。上级职责入口应直接列出下级子系统的契约入口，专题依赖另作说明，不另建全仓身份台账。

## 设计入口结构

任意层级的子系统入口都采用下面四个二级章节，单页子系统与目录子系统保持一致。专题页不套用子系统模板；如果某类操作没有长期实例，则在契约中说明它由哪个调用作用域承载。

| 章节 | 本级应解释的内容 |
|---|---|
| 职责与边界 | 职责概述、相邻边界及下级子系统入口 |
| Seam Contract | 本级契约的统一入口，按消费者问题导航到各 seam 的唯一正文 |
| 设计取舍 | 契约背后的非显然理由、代价与限制，不另定义调用义务 |
| 实现与验证入口 | 必要责任映射、status 差异与验证入口 |

契约划分、共同规则和六字段格式见[设计指南](../development/design.md#契约与责任)。

子系统入口须用单行 `上级契约：[名称](相对路径#章节)` 显式声明直接上级，并说明所细化的职责。上级可以是同目录的另一个单页子系统，不能由目录层级自动推定；顶层子系统则链接到系统边界。声明上级并不代表上级自动拥有全部底层资源，模块间的交互仍可构成网状关系。

### 契约页面组织

单项契约可直接使用六个三级字段标题。多项契约先用三级语义标题区分各个 seam，再在每个 seam 内用独占一行的加粗字段名组织六字段。必要细节使用唯一语义标题；如有需要，可设“共同规则”章节，明确适用范围和共同义务。

短契约优先留在同页；需要独立阅读时，再放到已有职责专题或按职责新建专题页。入口页用语义章节链接到外置契约的唯一正文，并点明消费者关心的问题。多个入口可以依赖同一份契约，但契约拥有者只有一个，导航摘要不复制完整规则。

章节划分应便于精确引用交接与依赖关系，不额外增加逐 seam ID、版本号或全量 API 台账。

## 关系用词与图形

| 用词 | 固定含义 |
|---|---|
| 上级生命周期 | 决定接纳或存续的作用域，不自动拥有底层资源的关闭权 |
| 状态写入者 | 修改并发布某份可变事实的主体 |
| 保留者 | 通过强引用、lease 或 pin 保活资源的主体 |
| 关闭责任方 | 执行最终关闭或发起规定清理动作的主体 |
| 借用者 | 只在指定窗口访问资源的主体 |
| 共享范围 | 允许复用同一资源的消费者范围，不等于共享可变状态 |

梳理非线性关系优先用拓扑图，比较 owner 职责或事件影响优先用表格，正文补充条件与例外。每张图都要说明抽象范围和边的含义，并用标签或线型区分请求、数据、持有关系与必需顺序。不要仅靠颜色表达语义，也不要把并行关系硬画成统一的状态机。简单的线性事实直接用文字陈述即可。

描述生命周期时，应严格区分以下几组概念：取消请求与实际终态、发布资格与合法旧使用、lease 关闭与物理回收、对象寿命与单次使用、服务结束与进程结束。图中和正文只记录必要的偏序关系。所有权转移须写明成功条件和失败后的清理责任；存在多个保留者，并不意味着存在多个关闭责任方。

## 实现信息准入

写入实现页的每个独立信息块都应同时通过以下三道门槛：

| 门槛 | 判断 |
|---|---|
| 架构关联 | 落实哪个具体契约、职责边界或关键设计选择？ |
| 独立增量 | 补充了哪个设计页未定义的必要写入者、门禁、转移点或共享身份？ |
| 最低精度 | 删掉具体结构、步骤或数值后，是否会丢失该责任关系？ |

保留下来的实现细节应能回答“删掉它会导致什么架构误判”。代码难读、局部算法易错、便于调试或“原本就写着”，都不能单独作为保留理由。可替换的责任映射仍可保留，不能仅因“未来可替换”就删除。产品和标准约束遵循各自的权威规则。

私有内存布局、具体算法步骤、调优数值、成员清单、测试快照和迭代过程通常不放进实现页；但只要通过上述三道门槛的必要责任关系，就可以保留。验证和状态证据直接链接到对应的权威入口。跨类、跨目录、跨线程或跨 Java 与 native 边界，都不自动构成架构边界；递归拆分也不降低信息准入门槛。局部实现知识是否需要注释或测试，应单独判断。

### 页面保留与定位

实现页乃至整个 `implementation/` 目录都是可选的。如果某个实现页只剩设计复述，直接删除；如果只剩少量责任符号，合并进设计页的“实现与验证入口”；只有在需要独立解释必要责任映射时，才保留专题实现页。不设篇幅或数量指标。

实现页开头须链接精确的设计章节并说明落实关系，符号引用遵循通用[写作约定](../documentation-rules.md#写作约定)。

## 流程与横向导航

`views/` 用于呈现跨职责树的关系视图或多场景比较，`flows/` 用于展开单个跨域场景。两者都是可选的，不套用子系统入口结构，不建自己的 `overview.md`，也不为同一问题重复建页。如果已有设计正文能独立说清关系，直接链接正文即可。

横向视图必须针对明确的阅读问题。为了连通拓扑或横向比较事件，允许重复必要的摘要，但每组关系都要精确链接到权威章节；光堆一组跳转链接不能代替跨域关系说明。

图形用于表达共享关系与必要偏序，并分别标明边的含义；表格按 owner 或事件比较归属、保留、关闭责任与结束条件。配额摘要须注明适用范围、计价对象和归还条件，不能把局部预算直接相加当作进程总内存上限。不要建立全量资源、成员、线程或参数台账。视图不能新增契约、囤积已被裁剪的实现细节，也不能替代实现页所依赖的设计正文。如果发现视图里出现了独有规则，先迁回实际责任方的设计正文，再在视图里保留摘要。

系统入口同时提供按问题导航与横向视图入口。只读视图应能把声明范围内的关系讲清楚，精确条件和例外则沿链接回到正文。视图的去留取决于阅读价值，不以“没有独有规则”作为删除理由。

## 修改与验证

修改文档时，先定位受影响的产品依据、权威设计和必要的当前映射，再按[信息取舍与维护](../documentation-rules.md#信息取舍与维护)筛选事实、修复引用，并按需同步更新产品 Landing、反向索引及复杂度依据。未落地的差异归入 `status`，尚未选定的方案归入 `future`。

完成后复核所有受影响的边界与场景，包括身份、决策方、写入者、保留方与关闭责任方、门禁及终态。确保只读父级就能看懂边界行为，折叠下级也不会改变契约语义。存在未解决的冲突时，不能仅因为链接有效就判定完成；发现依据缺口时定向核验代码或测试。

最后执行通用[文档检查](../documentation-rules.md#文档检查)。需注意，脚本检查只覆盖结构与引用，不代替对架构价值和消费者完整性的判断。
