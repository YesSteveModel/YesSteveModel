# 迁移概览

## 背景

旧版 YSM 的架构是在闭源、模型保护和减少攻击面的约束下逐步形成的。为了将模型格式、缓存、同步和加密逻辑隐藏在 native 层，Java 与 C++ 进行了深度绑定，C++ 最终承担了模型解析、缓存、同步、导出、烘焙、解码和渲染等大量职责。

这套系统能够完成从模型读取到多人同步和渲染的完整闭环，但代价也越来越明显：

* Java 与 C++ 之间存在大量业务级 JNI 接口，修改一个功能往往需要同时理解两侧实现。
* 许多模组业务语义被放在 C++ 中，调试、跨版本适配和自动化测试都比较困难。
* 旧架构缺少系统文档，又有较高的 C++ 门槛，实际维护工作长期集中在少数熟悉内部实现的人身上。
* 项目的保密要求进一步限制了代码交流和协作，使新人很难逐步参与。
* 即使对熟悉旧架构的维护者而言，继续扩展这套系统也越来越困难，部分工作长期处于缓慢推进甚至停滞状态。
* 这套盘根交错的设计与架构主要服务于旧版保护体系，项目开源后不再产生相应价值。

旧架构是特定约束下的解决方案。但项目准备开源后，继续沿用它会把已经失去意义的安全成本转化为长期技术债。因此新版工作的重点不是修补旧系统，而是重新划定职责边界，使主要业务可以被普通 Java 模组开发者理解、测试和扩展。

## 迁移方向

| 旧主线 | 当前主线 |
|---|---|
| C++ 拥有模型业务与同步状态 | Java 拥有格式语义、目录、授权、同步、导出、动画和生命周期 |
| 密钥、缓存与会话共同参与身份 | `ModelId` 表示业务身份，精确表示另行验证 |
| JNI 传递业务对象并驱动生命周期 | Protobuf、明确布局的 buffer 和 typed handle 只跨越能力边界 |
| 整包模型是同步与缓存单元 | 先发布描述，再按用途取得、验证和复用内容 |

Native 只保留压缩、hash、媒体、archive、bake / extract / render 等可替换能力，不拥有来源、权限、会话或缓存策略。跨语言职责和当前 owner 见[架构总览](architecture/README.md)。

## 当前位置

Asset Container、Model Schema、当前协议、Java 模型管理与动画主链、native CPU renderer 及 legacy 单向导入均已有实现入口，但“存在链路”不等于稳定、完整或通过产品验收。当前能力与证据只在[支持状态](status/support-and-verification.md)维护；具体缺口沿该页进入各主题已知问题。

历史输入只在系统边缘转换为当前制品。转换后的模型进入统一的目录、验证、资源和渲染流程，不保留第二套 legacy authority；可观察语义与容器冻结边界见[模型兼容](architecture/asset-pipeline/model-compatibility.md)。独立 Backend、外部模型源、统一模组动画接入和 GPU renderer 仍属于[未来方向](README.md)。
