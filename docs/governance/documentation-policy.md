# 文档政策

## 信息取舍

事实依据按主题确定。Wire 与格式以随文发布的规范和 schema 为准；当前支持状态以可复现的实现行为和验证结果为准。设计页定义职责、契约与取舍，实现页记录架构契约的必要落实关系。旧版 native 实现只用于理解历史原因，不能定义当前系统。

`product-decisions` 是其声明范围内产品目标、需求、业务约束、领域决策、决策理由与行为契约的 Root Authority。每项产品判断只有一个权威定义。Standard、architecture 与 status 可以摘要并链接对应产品决策，但不应重新定义产品判断。当前实现、验证状态或局部设计不能反向改写业务选择。

产品决策的分层、归约与变更闭环见[维护规则](../product-decisions/maintenance.md)。

只保留当前结论。需求、术语或设计发生修正后，直接更新为最终结果，不记录请求原文或纠错沿革。失效方案原则上删除；仍约束当前选择的经验，只保留约束和适用边界。

## 决策理由

架构选择与理由在所属子系统的设计入口及同级专题共同维护，带齐适用约束、选择、非显然理由、代价和限制。业务选择及其理由仍由 `product-decisions` 唯一拥有。设计不从当前机制反推产品承诺，也不把未经验证的性能动机写成收益。

同一规则只有一个权威定义。实现页描述落实该规则的状态与执行机制；横向视图与流程导航只重组摘要。已选择但未完全落地的设计链接 status 中的差异，不能静默改写设计或实现以制造一致。

临时 review ledger、实施计划、Phase、提交记录、旧验收清单和交接状态在决定闭环后退出长期权威。若某项理由只解释已经删除的中间方案，或其约束已被较新的设计取代，则直接删除；不要为保存重构过程把它改写成当前架构事实。

## 文档边界

- `product-decisions`：产品承诺、领域语义、必要边界及产品选择的理由。
- `standard`：语言无关的 wire、格式、schema、协议和一致性要求，应足以独立实现。
- `architecture`：系统核心模型；各子系统的 `overview.md` 与同级专题维护职责、契约和取舍，允许递归展开。
- 各子系统的 `implementation/`：架构契约在当前代码中的必要落实关系，可合并或删除。
- `architecture/views`：可选的跨域关系投影和场景比较；图表与必要摘要链接权威章节，不新增规则或承接已裁剪细节。
- `architecture/flows`：可选场景导航，只重组摘要，不新增规则或证明实现完成。
- `complexity-map`：机制因果、协调成本、证据与归约机会，不定义架构规则。
- `verification`：验证设施、复现方法与证据边界，不定义生产机制。
- `future`：尚未进入已选择设计的方向、进入条件和主要风险。
- `status`：支持矩阵与已知问题，不重复标准或架构正文。
- `reference`：压缩后的历史经验，不描述当前系统。

除 standard、schema 和 protocol 外，优先写概括和导航。设计与实现不按有无类名机械切分；改变一项事实是否要求重评架构选择，是判断其归属的依据。

## 归约与下沉

先判断信息是否值得保留，再选择唯一落点。上下层不逐层复述同一事实，也不要求被删除的正文全部转存下层。

- **产品到架构**：产品保留承诺的结果、领域语义和必要限制。可替换机制及其工程理由归架构；可观察的参数或行为不自动成为产品承诺。撤销既有承诺或约束、将其改为可替换机制，先按产品维护规则裁决。
- **设计到实现**：设计保留职责、契约、不变量及非显然取舍。无需重评这些选择即可替换的具体机制，按保留门槛进入实现页或删除。理由随其解释的选择归属，不把工程理由留在产品层。
- **实现保留门槛**：细节应支撑跨子系统契约或承重决策。承重决策指改变后需要重评兼容、安全、所有权、生命周期、失败边界或输出语义的选择。只服务于子系统内部的布局、计算步骤、调度与调优细节可以删除。局部算法需要正确、推导费力或难以从代码还原，均不单独构成保留理由。
- **复杂度投影**：地图记录机制解决的问题、根依据、协调成本、删除后果与归约条件，链接产品和架构的唯一正文。地图不承接实现细节，也不重复参数、规则或操作清单。产品层解除机制约束后，地图应同步复核必要性依据，不能继续将其归为产品必需。

归约以独立事实为单位。保留仍有效的条件、例外、顺序、所有权和失败边界；通识、直接推论和重复说明删除。概括或合并不能抹平独立义务，也不能用一个相近主题替代精确依据。架构的递归结构、关系用词、实现准入及引用闭环见[架构文档维护](architecture-docs.md)。其他层按各自维护规则执行。

## 写作规则

- 一个事实只设一个权威位置；其他页面摘要并链接。
- 当前、未来、历史和已知问题应分开，禁止把计划写成已实现能力。
- 组件按职责命名，例如 Java 领域层、native 能力层和旧版 native 实现；不以本机工程目录名代指项目或架构角色。
- 稳定包名、接口/类名及少量关键字段或方法名可以作为 owner、ABI/协议 seam、生命周期和正确性约束的定位锚点；不应附源码路径、行号或成员清单，也不应展开不承重的调用步骤使文档退化为代码导览。
- 涉及 Minecraft、Forge 时优先直接使用正式符号（如 `VertexConsumer`、`level`、`entity`、`tick`），不必复述模组开发常识；YSM 原创且无法由 Minecraft、Forge 或通用领域术语推知的稳定名称应在术语表统一释义。仅局部表达关键机制的函数或字段不扩成全局术语；standard、schema 或 protocol 已定义的局部 wire 符号也不重复收录。
- 使用相对链接；正式文档不应引用旧文档或本机路径。
- 不记录本机工程布局、IDE 工作区、检出路径、分支、commit 信息或文档时间。仅对一次本地构建或核查有意义的临时元数据也不进入正文。
- 格式、缓存和协议均处于 unstable 状态时，应明确说明，不使用“完全支持”“已经冻结”等绝对措辞。

正式文档应自包含，不依赖已弃用资料才能解释当前系统。

验证投入与证据解释见[验证边界](verification-policy.md)；验收流程不作为产品判断节点，产品软目标也不能由验证流程反向重定义。
