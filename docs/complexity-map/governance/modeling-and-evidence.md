# 建模、证据与计数口径

本页只定义所有子系统共用的分类标准、证据等级、节点口径和全局验证边界；各子系统的实际覆盖范围、根键、关系视图与未决缺口由对应本地页面维护。

## 分类与证据

必要性分类用来区分机制的约束来源：
- `Essential`：当前业务或外部契约直接要求的义务。它保护的是义务本身，并不把当前协议、缓存或状态表示固化为唯一实现。
- `Derived`：依赖可修改上游选择的现存机制。
- `Historical`：已证实原前提消失但机制仍在。当前图中没有足够证据将任何机制标为 `Historical`；旧注释、未找到消费者或不符合新契约，都不等价于已证实可删除。
- `Uncertain`：必要性尚未确认。

证据等级附着于具体结论和关系边，与必要性分类相互独立：
- `Fact`：引用材料直接支持该结论。
- `Inference`：有较强依据支持但缺少直接记录，必须同时保留支持事实和更弱的竞争解释。
- `Hypothesis`：多种解释尚未排除，必须保留归约影响与最小验证入口。

架构文档只能证明“规定如此”，源码可以证明当前选择、必要条件或删除后的失败后果，但两者都不能证明未记录的历史动机。各机制页列出的“直接删除失败”均在保持其他设计不变的反事实前提下成立；如果替换上游方案，部分失败条件可能不再可达。

节点按语义建模：
- `D`、`C`：产品决策或外部根约束。
- `A`：内部架构选择。
- `P`：衍生出的问题或失败机会。
- `AP`、`MN`、`AN`、`NR`：各子系统的具体机制。
- `H`：待验证的假设根。

类、方法、文件和字段仅作为证据导航，同一语义跨不同实现不重复计数。机制簇不参与计数；必要性、上游前提或退出条件不同的成员各自保留独立条目。

## 全局验证边界

全图记录 64 个生产机制。这一数字仅反映文档拆分粒度，不代表系统复杂度高低，也不表示已穷尽所有机制。维护地图时复用已有机制证据，并针对变化和缺口定向核验当前源码，并未逐条重新审计全部实现。CodeGraph 与 GitNexus 仅用于生成结构候选，存在不确定分派、重载歧义或 `.inc` 缺边时，不能直接补成因果边。文档检查（链接、Mermaid、ID、关系与计数）只提供静态证据，不替代游戏运行、Gradle 或 CMake 构建及性能验收；机制页引用的测试也只覆盖各自观察边界。

Java 机制页引用测试作为可定位的行为断言，不把测试名称或静态调用关系当作运行通过的证明。完整格式 golden、真实 GUI 反复翻页与关闭、GPU 纹理回收和实机模型外观仍受[支持与验证边界](../../status/support-and-verification.md)约束。

[Mock 验证设施](../../verification/model-management.md)中的进程监督、物理 classpath 隔离与证据汇总属于测试协调，不计入生产机制；通过其中某一层也不代表其他层的未验项已获确认。精确读取实例、converted 消费者与清理、页面批量请求的失败处理分别展开于 MN-05、MN-24 与 AP-04，不按验证场景另增节点。

关系类型与按需加载规则见[关系登记入口](relationship-register.md)；Fact 边由四个子系统关系页和[跨子系统关系](cross-subsystem-relations.md)唯一维护，全局计数见[高扇出候选](global-fanout.md)，根键解释见[根依据总表](root-register.md)。
