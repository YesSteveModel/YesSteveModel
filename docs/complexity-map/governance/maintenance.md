# 维护与复杂度归约规则

本页用于新需求开发、机制归约和地图维护。遵循[文档治理规则](../../documentation-rules.md)和[验证边界](../../verification/policy.md)；产品判断的变更按[产品决策维护规则](../../product-decisions/maintenance.md)闭环。

本图不要求兼容现存机制。任务可修改或替换机制以降低整体复杂度；大范围复杂度归约需要人工仲裁。

## 从文档定位义务与候选

归约分析从目标范围内的[产品决策](../../product-decisions/README.md)、[系统架构](../../architecture/README.md)和本图出发，分别确认产品义务、架构边界、机制来源及派生负担。设计中的实现入口定位必要的当前责任映射。

上游规则下沉或撤销时，分别复核产品义务、当前机制和必要性分类；产品不再约束某个机制，不代表该机制已经删除。已完成的归约不保留过程叙述，仍有效的独立义务归入机制正文。

从本图的机制或子图定位候选，沿架构入口和产品稳定 ID 读取相关完整边界，形成承接关系及待验证问题。缺少必要产品义务或关键架构边界时，列出缺口并暂停依赖该缺口的判断；维护地图时记录未闭合的缺口，不因此删除节点。

源码用于核验关键缺口、文档冲突、当前消费者、替代或删除条件与实现验收。沿已发现的跨边界关系定向查询，取得足够证据后回到文档比较。规定与观察冲突时分别记录，不能用文档覆盖实现事实，也不能用当前实现替产品裁决。

## 最小机制空间

协调机制及方案成本的通用判断见[设计指南](../../development/design.md#从结果选择机制)。

开发新需求需要新增复杂协调机制时，执行以下判断：

1. 明确需求要求保持的行为、invariant、失败边界及证据。从相关机制页沿上游原因、共享依赖和派生关系寻找维护同一问题或前提的机制，不只查高扇出列表。
2. 优先评估复用、扩展已有机制，或修改共同上游边界以统一归约。比较保留原方案、复用 / 归约和新增替代方案；复用若引入更宽 ownership、生命周期耦合、模式组合或恢复分支，不因“没有新增机制”而优先。
3. 涉及替代旧机制时，逐项核对旧机制的有效职责是否已被完整承接，包括共享消费者、独立约束及“直接删除会发生什么错误”。确认完整替代后，在本次授权实现范围内删除旧机制及仅为它服务的状态、guard、恢复、兼容和协调逻辑；部分承接只删除被覆盖部分，保留仍有独立理由的义务。未找到用途不是删除证明，已证实冗余也不能仅以防御为由继续保留。
4. 按影响选择代表性的正常、并发、生命周期或失败场景，核验承接关系与净收益，运行最小相关测试或性能比较。若需要暂时双轨，明确具体未承接义务、切换条件和旧路径退出条件；旧路径未退出时报告为未完成归约。仅生成或维护文档时记录判断与验证缺口，不执行代码删除或把替代计划写成已实现。

主动归约已有机制也采用以上判据：优先检查已失效前提、重复维护同一 invariant 的机制，以及只服务于另一内部机制的机制树；允许用更统一的新机制替代它们。既有产品契约不能通过归约暗中放宽；涉及产品选择变化时先完成相应裁决。

## 地图同步与验收

- **触发与范围**：机制新增、合并、拆分、替换、删除，上游决策或前提变化，以及新证据出现时，定位相关节点并复核其上下游与共享消费者。主体继续覆盖重要的低扇出、局部和来源未明机制；局部核验不能扩大全图覆盖声明。
- **证据与关系**：沿用[建模、证据与计数口径](modeling-and-evidence.md)及[关系登记](relationship-register.md)的定义；保留机制直接问题、删除失败、根依据及附属机制。当前行为不替历史动机背书；规定与观察冲突时分开记录，无法闭合的原因写入具体缺口及最小核验入口。
- **唯一落点、ID 与退出**：每个机制在所属机制页只有一条正文定义；本页总览、关系表、图和排名都是该事实的投影。语义延续保留 ID；替换为不同机制时分配新 ID，拆出的独立义务获得新 ID，原 ID 仅保留仍延续的语义。拆合删前承接仍有效的事实、关系与未决问题，并检查文档内外入链；实际删除后退出当前集合与计数，不能以 `Historical` 留存已删除机制，也不能将旧根因套到新机制。只保留仍解释存活机制的历史来源，已裁决问题退出争议页。
- **联动内容**：实现归约后同步受影响的源码、测试、架构和本图。地图内按影响更新机制正文、根依据、关系分片、Mermaid 投影、必要性、未决项、支点和统计；关系只在一个 owner 分片出现。Fact 关系或机制集合变化时，从全部 Fact 分片复算全局 R/D，重新核对可消失部分和剩余独立义务。
- **最小检查**：从仓库根目录运行 `python docs/tools/check_docs.py` 与 `git diff --check`。前者调用 `check_complexity_relationships.py`，核对机制 ID、关系唯一性、分片归属、端点及全局 R/D。检查受影响的 Mermaid 图，确保每条边属于关系分片，折叠集合不产生额外边；修改 Mermaid 时执行渲染校验。实现发生变化时按影响执行最小相关构建或测试；文档与图检查不能证明运行行为、性能或旧路径退出。
