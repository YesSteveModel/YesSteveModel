# 维护与复杂度归约规则

本节可独立用于新需求开发和已有机制维护，无需读取生成本图的 skill。遵循[文档政策](../../governance/documentation-policy.md)和[验证边界](../../governance/verification-policy.md)；实现调整限于任务授权范围，产品判断的变更仍按[产品决策维护规则](../../product-decisions/maintenance.md)闭环。本图不将现存机制提升为必须兼容的契约。

## 从文档定位义务与候选

归约分析以前置的三类现有材料为基线：[产品决策](../../product-decisions/README.md)说明不能暗中删除的行为及其理由，[系统架构](../../architecture/README.md)及子系统设计定义 ownership、invariant、生命周期与失败边界，设计中的实现入口定位必要的当前责任映射，本图说明机制来源、共享依赖与派生负担。只要求覆盖本次目标范围，不要求固定文件数量、重写成特定格式或通读整棵文档树。

地图的信息取舍遵循[归约与下沉](../../governance/documentation-policy.md#归约与下沉)。上游规则下沉或撤销时，分别复核产品义务、当前机制和必要性分类；产品不再约束某个机制，不代表该机制已经删除。已完成的归约不保留过程叙述，仍有效的独立义务归入机制正文。

从本图的机制/子图定位候选，沿架构入口和产品稳定 ID 读取相关完整边界，先形成承接关系及待验证问题。缺少必要产品义务或关键架构边界时，列出最小补齐内容，暂停依赖该缺口的判断；不能从现存代码猜造产品决定，也不自动转入全项目文档生成或代码考古。单纯维护地图可记录明确缺口，不能因未闭合而删除节点。

源码用于核验关键缺口、文档冲突、当前消费者、替代/删除条件与实现验收。每次查询先说明要回答的问题、已知文档/符号入口和足够证据，优先复用同一实际工作树的索引，按已发现的跨边界关系扩大范围，答案闭合即回到文档比较；不无条件遍历代码或重建全仓图。规定与观察冲突时分别保留，不能用文档覆盖实现事实，也不能用当前实现替产品裁决。等价内部机制替换不因查过产品文档就要求重新修改产品决定。

## 最小机制空间

目标是满足当前业务需求与有效约束的**最小机制空间**，不是每次改动都严格减少机制数量。可以新增一个统一机制，消除大量旧机制及其派生协调；比较的是最终整体可达状态空间、ownership、生命周期交错、跨域协调和恢复负担，并计入迁移成本。不能以少几个类、状态字段、图节点或代码行证明归约；封装、改名和把复杂度转移到另一层也不算收益。结论限定于已评估范围，不声称全局最优。

设计从可观察的产品结果和必须成立的 invariant 出发；只有现有生命周期无法收敛明确风险，且新机制能排除更大的可达状态空间时，才支付它的长期状态、恢复、兼容与迁移成本。一个事实只设一个 authority，一个生命周期只设一个 owner；已接受的 commitment 必须到达终态，逻辑责任与物理回收分别闭环。有限容量不得隐藏对外部进展的依赖，退役以旧工作不再可能产生可见副作用为准；提交只在最小可观察范围原子化，失败保留 provenance 并优先借现有生命周期收敛。抽象必须承载真实契约或独立变化原因，任何完成与可靠性结论都不得超过验证证据的覆盖范围。

对运行稳定性和最终结果影响不大的局部不确定性，可以保留；不得只为把低价值的局部选择变成确定结果而增加跨域排序、持久状态或恢复协议。低概率且无法安全消歧的情况，默认在最小所属边界显式拒绝或硬失败，不以猜测或新增协调机制掩盖歧义。只有该处置会破坏核心日常用例、造成不可接受的数据丢失，或把普通输入升级为 startup 级故障时，才考虑增加机制；新增仍须证明风险收敛收益超过长期状态、恢复和验证成本。

开发新需求需要新增复杂协调机制时，执行以下判断：

1. 明确需求必须保持的行为、invariant、失败边界及证据。从相关机制页沿上游原因、共享依赖和派生关系寻找维护同一问题或前提的机制，不只查高扇出列表。
2. 优先评估复用、扩展已有机制，或修改共同上游边界以统一归约。比较保留原方案、复用 / 归约和新增替代方案；复用若引入更宽 ownership、生命周期耦合、模式组合或恢复分支，不因“没有新增机制”而优先。
3. 评估后仍需新机制时，逐项核对旧机制的有效职责是否已被完整承接，包括共享消费者、独立约束及“直接删除会发生什么错误”。确认完整替代后，在本次授权实现范围内删除旧机制及仅为它服务的状态、guard、恢复、兼容和协调逻辑；部分承接只删除被覆盖部分，保留仍有独立理由的义务。未找到用途不是删除证明，已证实冗余也不能仅以防御为由继续保留。
4. 用代表性正常、并发、生命周期和失败场景核验承接关系与净收益，按影响运行最小相关测试或性能比较。若必须暂时双轨，明确具体未承接义务、切换条件和旧路径退出条件；旧路径未退出时报告为未完成归约。仅生成或维护文档时记录判断与验证缺口，不执行代码删除或把替代计划写成已实现。

主动归约已有机制也采用以上判据：优先检查已失效前提、重复维护同一 invariant 的机制，以及只服务于另一内部机制的机制树；允许用更统一的新机制替代它们。既有产品契约不能通过归约暗中放宽；涉及产品选择变化时先完成相应裁决。

## 地图同步与验收

- **触发与范围**：机制新增、合并、拆分、替换、删除，上游决策或前提变化，以及新证据出现时，定位相关节点并复核其上下游与共享消费者。主体继续覆盖重要的低扇出、局部和来源未明机制；局部核验不能扩大全图覆盖声明。
- **证据与关系**：沿用本页定义的节点、边方向、必要性分类和证据等级；保留机制直接问题、删除失败、根依据及附属机制。当前行为不替历史动机背书；规定与观察冲突时分开记录，无法闭合的原因写入具体缺口及最小核验入口。
- **唯一落点、ID 与退出**：每个机制在所属机制页只有一条正文定义；本页总览、关系表、图和排名都是该事实的投影。语义延续保留 ID；替换为不同机制时分配新 ID，拆出的独立义务获得新 ID，原 ID 仅保留仍延续的语义。拆合删前承接仍有效的事实、关系与未决问题，并检查文档内外入链；实际删除后退出当前集合与计数，不能以 `Historical` 留存已删除机制，也不能将旧根因套到新机制。只保留仍解释存活机制的历史来源，已裁决问题退出争议页。
- **联动内容**：实现归约后同步相关源码、测试、架构和本图。地图内同步机制正文、根依据、所属子系统关系分片、跨域关系、Mermaid 投影、必要性、未决项、支点和统计，不能只删节点或改局部正文。关系只在一个 owner 分片出现；全局 R/D 从全部 Fact 分片复算，重新核对可消失部分和剩余独立义务。
- **最小检查**：从仓库根目录运行 `python docs/tools/check_docs.py` 与 `git diff --check`，检查相对链接、锚点、自包含和格式。该脚本会调用同目录的 `check_complexity_relationships.py`，核对机制 ID、关系唯一性、分片归属、端点及全局 R/D。另需核对 Mermaid 逐边属于关系分片，折叠集合不得产生额外边；用可用 Mermaid CLI 对图执行渲染校验，缺少工具时至少预览并逐边检查，说明未执行语法渲染。只有实现发生变化才按影响执行最小相关构建/测试；文档与图检查不能证明运行行为、性能或旧路径退出。
