# 维护与复杂度归约规则

本页用于指导新需求开发、机制归约和复杂度地图的日常维护。维护工作遵循[文档治理规则](../../documentation-rules.md)与[验证边界](../../verification/policy.md)；涉及产品判断调整时，按[产品决策维护规则](../../product-decisions/maintenance.md)同步更新上游决策。

本图不把现存机制当作必须兼容的契约。开发任务可以修改或替换机制以降低整体复杂度，但涉及大范围复杂度归约时，仍需人工仲裁。

## 从文档定位义务与候选

归约分析先从目标范围内的[产品决策](../../product-decisions/README.md)、[系统架构](../../architecture/README.md)和本图入手，分别查清产品义务、架构边界、机制来源和派生负担，再通过设计文档中的实现入口定位当前的责任映射。

当上游规则下沉或撤销时，需要分别复核产品义务、现存机制和必要性分类：产品不再约束某个机制，并不意味着它已在代码中删除。已经完成的归约无需保留过程叙述，仍然有效的独立义务直接并入机制正文。

定位候选机制或子图后，沿架构入口和产品稳定 ID 读完相关完整边界，梳理清楚职责承接关系和待验证问题。如果缺少必要的产品义务或关键架构边界，先列出缺口并暂停依赖该缺口的判断；维护地图时把未查清的缺口记下来，不要直接删掉对应节点。

源码检索用来核验关键缺口、文档冲突、当前消费者、替代或删除条件，以及最终的实现验收。查询时沿已发现的跨边界关系定向展开，拿到足够证据后回到文档比对。一旦发现文档规定与代码观察冲突，双方分别记录——既不能用文档覆盖实现事实，也不能拿当前实现替产品做决定。

## 最小机制空间

关于协调机制与方案成本的通用判断标准，见[设计指南](../../development/design.md#从结果选择机制)。

开发新需求且考虑新增复杂协调机制时，按以下四步评估：

1. **先查清已有机制**：明确需求必须维持的行为、不变式（invariant）、失败边界及验证证据。从相关机制页沿上游原因、共享依赖和派生关系排查，找出正在维护同一问题或前提的机制，不要只看高扇出列表。
2. **权衡复用、归约与替换**：优先评估复用或扩展已有机制，或者调整共同上游边界来统一简化，并横向比较“保留原方案”“复用或归约”和“新增替代方案”。如果复用反而引入更宽的所有权、生命周期耦合、模式组合或恢复分支，不能仅仅因为“没有新增机制”就优先选它。
3. **核对完整承接与清理范围**：需要替代旧机制时，逐项核对它的有效职责是否已完整承接，包括共享消费者、独立约束以及“直接删除会引发什么错误”。确认完整替代后，在本次授权实现范围内一并删除旧机制以及专为它服务的状态、门禁、恢复、兼容和协调代码；若只是部分承接，则只删被覆盖的部分，保留仍有独立理由的义务。没找到用途不等于可安全删除，而已经证实冗余的代码也不应以“防御”为由继续保留。
4. **验证净收益并管好过渡**：按影响面挑选代表性的正常、并发、生命周期或失败场景，核验承接关系与净收益，并运行最小相关测试或性能对比。如果确实需要暂时双轨，必须写清尚未承接的义务、切换条件和旧路径退出条件；只要旧路径未退出，就报告为“未完成归约”。仅编写或维护文档时，只记录判断与验证缺口，不删除代码，也不把替代计划写成既成事实。

主动归约已有机制同样适用上述判据：优先排查前提已失效的机制、重复维护同一不变式的机制，以及只服务于另一内部机制的整棵派生树，并允许用更统一的新机制替代。但归约不能暗中放宽既有产品契约；只要涉及产品选择变化，必须先完成对应上游裁决。

## 地图同步与验收

- **触发与范围**：每当机制发生新增、合并、拆分、替换、删除，或上游决策、前提条件与新证据变化时，定位受影响节点并复核其上下游及共享消费者。地图主体继续覆盖重要的低扇出、局部和来源未明机制；局部核验不能夸大成全图覆盖声明。
- **证据与关系**：沿用[建模、证据与计数口径](modeling-and-evidence.md)和[关系登记](relationship-register.md)的标准，保留机制解决的直接问题、直接删除导致的失败、根依据及附属机制。当前代码行为不能为未记录的历史动机背书；规定与观察冲突时分开记录，尚无结论的部分写明具体缺口和最小核验入口。
- **唯一落点、ID 与退出**：每个机制只在所属机制页保留一条正文定义，总览、关系表、图和排名都是该事实的派生视图。语义延续时保留原 ID；替换为不同机制时分配新 ID；拆出的独立义务分配新 ID，原 ID 仅保留延续下来的语义。在拆分、合并或删除前，先承接好仍有效的事实、关系和未决问题，并检查文档内外的入链。机制实际删除后即退出当前集合与计数，既不能标成 `Historical` 留在表里，也不能把旧根因套在新机制上；历史来源只保留仍在解释存活机制的部分，已决断的问题则退出争议页。
- **联动更新**：实现归约后同步更新受影响的源码、测试、架构文档和复杂度地图。地图内按影响范围同步机制正文、根依据、关系分片、Mermaid 视图、必要性分类、未决项、归约支点和统计数据，确保每条关系只出现在唯一负责的分片中。一旦 Fact 关系或机制集合发生变化，必须从全部 Fact 分片重新计算全局 R/D，并复核可消除部分与剩余独立义务。
- **最小检查**：在仓库根目录运行 `python docs/tools/check_docs.py` 和 `git diff --check`。前者会联动调用 `check_complexity_relationships.py`，核对机制 ID、关系唯一性、分片归属、端点合法性及全局 R/D。同时检查受影响的 Mermaid 图，确保每条边都来自关系分片，且折叠集合没有引入额外边；修改 Mermaid 后须完成渲染校验。如果改动了代码实现，按影响执行最小相关构建或测试——文档和图检查只保证静态一致性，不替代运行行为、性能或旧路径退出的验证。
