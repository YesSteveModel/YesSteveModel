# 代码契约

本页是[实现指南](implementation.md#代码契约)的声明格式参考。Seam 的划定范围、职责划分与总体语义由[设计指南](design.md#契约与责任)定义。

## 声明位置与格式

代码契约要回答三个问题：调用方必须满足哪些前提、提供方据此建立并维持哪些保证，以及正常失败与调用违约分别由谁处理。每项保证都应交代清楚作用对象、有效时间窗口以及何时失效。

| 位置 | 承载的信息 |
|---|---|
| 类型、注解、签名 | 编译器或工具可识别的范围、可空性、结果分支、只读性和所有权约束 |
| seam 接口或类声明 | 实例不变量、共享的生命周期与并发规则、对应的架构条款 |
| seam 方法声明 | 本次调用的前置条件、结果保证、失败语义、执行方式及资源交接 |
| seam 暴露的字段或数据类型 | 取值范围、状态关联、访问权限及引用有效期 |
| 实现内部 | 如何建立和维持上述保证，以及不显然的设计理由 |

声明直接写在普通 Javadoc 里：参数、返回值和异常使用标准标签，其余补充段落按以下名称和顺序按需填写。

| 段落 | 说明内容 |
|---|---|
| `Invariant` | 实例或字段在指定可观察窗口内始终成立的不变量 |
| `Requires` | 调用方必须满足的前置条件以及可继承的输入保证 |
| `Ensures` | 调用成功后的返回值、状态变化、副作用及其关联关系 |
| `Failure` | 合法失败的触发条件、报告通道、状态与资源后果及恢复责任 |
| `Execution` | 执行线程、是否阻塞、返回的完成含义、并发粒度、原子性与重入规则 |
| `Ownership` | 保留、借用、所有权转移和关闭责任，区分成功、失败与取消路径 |
| `Seam` | 落实或依赖的具体架构契约条款，以及本类或本方法承担的那部分责任 |

`Invariant` 与 `Seam` 通常放在类型声明上。方法默认继承类型的共同规则，只写自身增量，也不在段落里复述标准标签或类型签名已经写明的内容。不适用的段落直接省略，不要填空模板；但省略只表示不适用或已由共同规则覆盖，绝不意味着“支持任意线程”“永不失败”或“可以长期持有”。

## 输入、结果与字段

契约要区分“调用前置条件”和“提供方接纳规则”。以索引范围 `[0, capacity)` 为例：如果它是前置条件，说明调用方必须保证索引合法；如果它是接纳规则，说明提供方会校验原始索引并按约定通道拒绝越界值。前置条件本身不要求提供方额外写运行时检查，而针对调用违约的诊断也不应伪装成正常的业务拒收协议。

| 对象 | 类型本身无法表达时应补充的条件 |
|---|---|
| 数值 | 单位、开闭区间、特殊值含义；浮点数是否允许 `NaN` 或无穷大 |
| 参数关系 | 长度与容量、身份与作用域之间的对应关系；偏移和长度的单位及无溢出约束 |
| 可空性 | 参数、返回对象、集合元素和嵌套字段分别是否可空，以及 `null` 的唯一含义 |
| 集合与视图 | 元素顺序、是否允许重复、空集合含义、返回的是快照还是实时视图、元素是否可变 |
| buffer 与 native 地址 | 有效范围、对齐要求、可写性、别名限制、`position`/`limit` 是否变化及借用窗口 |
| 字段 | 合法状态下的取值范围与字段间关联、允许谁写入、读取窗口及不变量的生效时点 |

缺失值处理、可变输入和保证维持见[实现指南](implementation.md#数据与失败)。

字段不变量要区分“内部修改过程中的临时状态”和“对外可观察窗口”。只有当字段约束确实影响 seam 消费方的调用或访问方式时才需要声明，普通私有字段不必逐项填写。

## 失败与异常

每一类允许发生的失败都要交代四件事：触发条件、报告通道、状态与资源后果，以及由谁决定如何恢复。

| 类别 | 声明要求 |
|---|---|
| 正常否定结果 | 缺失、Busy、过期、拒收等明确返回分支，以及此时是否产生副作用 |
| 运行失败 | I/O 错误、设备异常、执行器拒收等失败的报告通道，以及提交与清理状态 |
| 调用违约 | 明确责任方与诊断语义，不能把违约包装成正常缺失、cache miss 或成功 |
| 内部不变量破坏 | 指定诊断与故障隔离边界，不要求每个消费方各自写恢复逻辑 |

合法调用可能触发的业务失败应当划清范围。没有列出的实现缺陷不会自动变成“正常可恢复结果”，没写出来的未受检异常也不自动构成“绝不抛出”的承诺。同步抛异常和异步完成失败需要分开说明。

描述失败后的状态时，应区分未提交、部分提交，以及已提交但通知失败；支持重试的接口必须写明重复副作用、操作身份和幂等性条件。

`Error`、进程级故障和整体隔离策略直接引用指定的上层边界即可。

## 执行、并发与状态

不要只写一句笼统的“线程安全”“异步执行”或“加锁保护”来代替执行契约。按接口实际涉及的行为，明确以下维度：

| 维度 | 需要写清的内容 |
|---|---|
| 执行位置 | 在调用线程、指定 owner 线程还是后台工作线程执行；调用方是否负责切线程 |
| 返回与完成 | 方法返回代表请求已创建、已接纳、已提交还是已执行完；完成是否包含发布或安装 |
| 阻塞行为 | 是否会等待 I/O、其他任务或 owner 线程；在热路径上有哪些限制及前提 |
| 并发范围 | 并发控制针对单个实例、单个 key、单个资源还是整个服务；哪些操作允许重叠执行 |
| 原子性 | 原子性覆盖单次调用还是组合操作；与关闭、替换、撤销之间如何排序 |
| 可见性 | 从哪个交付点起消费方能看到完整结果，之后是否允许修改 |
| 回调语义 | 回调是否可能内联执行、在哪个线程执行、执行时是否持锁、是否允许重入以及异常归属 |
| 取消与终态 | 取消只是发出请求还是已确保停止；借用何时结束，谁负责释放迟到或无人认领的结果 |

状态查询方法必须说明返回值是瞬时快照，还是持续有效的使用资格，并注明它与失效事件之间的先后顺序或有效窗口。相关设计原则见[设计指南](design.md#权威所有权与提交)。

重复调用要写明是幂等成功、正常拒绝还是调用违约。`close()` 要分别交代三件事：对在途工作的影响、对已交付资源的影响，以及关闭后发起新操作的结果。对象本身仍然存活可用，不自动意味着它仍有资格参与新的操作。

返回异步句柄的接口，必须写清任务如何走到终态、结果如何交付，以及在无人接收或中途取消后由谁清理资源。

## 声明示例

以下虚构接口仅用于演示注释格式，不代表当前实现。假定 `Candidate` 与 `InstallResult` 自身的类型契约已经规定了内容合法性、非空引用和结果分支；在真实代码中，类型注释里的 `Seam` 段落应链接到具体的架构契约小节。

```java
/**
 * Owns the installed candidate.
 *
 * <p>Invariant: the slot is empty or owns one complete candidate.
 *
 * <p>Execution: confined to the render owner thread, including close().
 * Calls do not invoke external callbacks.
 *
 * <p>Seam: refines complete installation and replacement.
 */
interface CandidateSlot extends AutoCloseable {

    /**
     * Attempts to replace the installed candidate.
     *
     * <p>Requires: the caller owns candidate exclusively.
     * Candidate must not be the currently installed instance.
     *
     * <p>Ensures: INSTALLED transfers ownership to this slot and
     * releases the previous candidate. CLOSED leaves the slot unchanged
     * and candidate owned by the caller.
     *
     * <p>Failure: a closed slot returns CLOSED. A valid call has no
     * recoverable exception outcome.
     *
     * <p>Execution: completes on the calling thread before returning.
     * Requires the render owner thread.
     *
     * @param candidate the candidate whose ownership may be transferred
     * @return the installation outcome
     */
    InstallResult tryInstall(Candidate candidate);

    /**
     * <p>Ensures: closes the slot and releases its installed candidate.
     * Repeated calls leave the slot closed.
     *
     * <p>Failure: a valid call has no recoverable exception outcome.
     *
     * <p>Execution: completes before returning on the render owner thread.
     */
    @Override
    void close();
}
```

按这份契约，调用方无需重复校验 `candidate` 的完整性、不必先查询关闭状态，也不必在外层加锁；但调用方仍须满足线程前置条件，并在返回 `CLOSED` 时自行处理 `candidate` 的后续释放。如果实际实现还可能因资源上传失败而拒收，就应该要么在交接前完成构建，要么在契约中如实声明失败路径与资源后果。

## 与架构契约的连接

代码契约是对[架构契约](design.md#架构契约格式)六个字段的代码级细化：

| 架构字段 | 在代码声明中的对应落实 |
|---|---|
| 边界与权威 | 负责判断权威状态和执行写入的具体接口或实例 |
| 前置条件与输入 | `Requires`、参数类型以及接纳规则 |
| 结果与保证 | `Ensures`、返回分支与实例不变量 |
| 所有权与时序 | `Ownership`、`Execution` 以及状态与生命周期方法 |
| 失败与拒收 | `Failure`、异常通道以及失败后的状态与资源归属 |
| 证据与依赖 | 建立与维持机制、验证入口（测试通过状态不写进 API 注释） |

边界类型应链接到具体 seam 的架构小节，并写明自己落实或依赖了其中哪项职责。同一个类如果同时实现多个 seam，类型注释只写共享约束，具体职责分别标在对应的接口或方法上；不要用整个子系统的导航页去糊弄所有方法的契约关联。方法默认继承类型上适用的关联，承担额外职责时再单独引用。相应地，架构文档只点名少量关键责任类型，不维护全量 API 清单。

源码注释中书写文档链接的格式见[实现指南](implementation.md#源码注释的文档引用)。

代码注释应足以让调用方正确使用接口，跨模块的组合前提与不显然的设计权衡则沿链接去架构文档里读。同一条规则只保留一份权威定义——声明处可以给出必要的精简摘要或参数级具体化，但不要另写第二套规范。

举个例子：架构契约规定“撤销缓存引用不会关闭仍被消费方持有的资源”。落到代码契约时，就需要明确哪个返回值持有 lease、谁负责调用 `close()`、借用值在什么时点失效；至于底层如何引用计数或保活，留给实现层即可。如果某个方法新增的前置条件导致架构原本允许的调用方式不再成立，应回到架构层重评边界，而不是只补一行注释了事。
