# 实现指南

本页规定实现阶段的总则，说明如何在代码中落实并维持契约保证、正确使用上游依赖，以及如何传播变更与开展验证。实现以[设计指南](design.md)确定的契约和职责为输入；代码声明格式见[代码契约](code-contracts.md)，现有基础设施见[基建指南](infrastructure.md)，审查口径见[分层审查](review.md)。

## 实施原则

动手改代码前，先明确要解决的问题、关键假设和可验证的目标结果，并核对设计文档与当前源码。修复缺陷时，优先复现问题并定位根因；如果已有结论的依据和前提没有变化，直接沿用即可。实现过程中一旦发现契约缺口、语义冲突或预期之外的可观察行为变化，应退回设计阶段重新确认；涉及产品语义冲突时，交由维护者拍板。

改动应聚焦在本次任务及必须联动修改的依赖上，保留工作区中用户已有的改动。替换旧机制时，先确认仍有效的职责已被新机制接管，再清理失效路径和残留代码；如果存在多个会影响对外行为或长期维护成本的方案，按[设计总则](design.md#从结果选择机制)说明取舍理由。

当目标设计已经敲定，且当前方案满足契约、受影响位置均已同步更新并通过验证后，不要为了追求更短的代码继续反复尝试替代写法；只有发现具体缺陷、未解疑点或明确的成本证据时，才重新打开方案比较。

简短、只用一次且紧贴局部上下文的逻辑，默认就地写清楚即可。抽取独立函数应带来实际收益——例如多处复用、隔离复杂逻辑、收紧资源或副作用的作用域，或减轻阅读主流程的负担；如果只是单纯转发参数，或者仅仅为了“以后可能复用”，通常不值得抽取。

需要多人或多任务分工时，按可独立交付和独立验证的结果拆分。在启动彼此依赖的子任务之前，先敲定共享接口、资源归属和依赖关系，并明确由谁负责最终集成与整体验证。

## 使用保证与保护责任

依赖某个 seam 之前，先读清它的显式共同规则、上游依赖和代码声明。首次接入、前提条件变化或出现反例时，要核对这项保证是在哪里建立的、由谁维持、在什么时间窗口内有效——建立入口必须覆盖所有进入路径，维持方必须管住所有可能破坏保证的操作。

调用方应直接信任上游已经建立且持续有效的内部不变量。提供方负责维持结果保证，并妥善处理失败、取消、拒收以及未交付出去的资源；调用方负责满足输入前提、做好多步组合、按需恢复以及按约归还资源。注意，仅仅因为代码在同一个仓库、同一个进程里，或者写过注释、以前通过过验收，本身并不构成运行时保证。

决定新增或删除任何保护性代码时，必须说清它要防范的独立失败来源是什么、责任归谁以及有效窗口有多长；不要机械地把接口前置条件逐条翻译成运行时检查。

| 保护手段 | 核对要点 |
|---|---|
| 判空、范围、完整性或输入校验 | 对象的构造和修改入口是否受控；已有保证是否覆盖当前需求和使用窗口 |
| 捕获异常、fallback | 当前层是否真的承担恢复、异常翻译或故障隔离职责 |
| 外部锁、内存屏障 | 并发粒度、内存可见性与失效事件的先后顺序是否已被内部机制覆盖 |
| 关闭、就绪或身份查询 | 实际操作是否原子地完成检查与执行；查询到的是持续资格还是瞬时快照 |
| 防御性拷贝 | 底层数据是否不可变；借用窗口内是否已排除并发修改和提前释放 |
| 重试与恢复状态 | 重试策略、重复副作用和失败后的资源去向是否已在上游处理 |

删除原有保护时，要明确交代原职责是由哪个建立点或机制接管了，或者因合法使用范围收窄而不再存在。同时仍需守住资源保活、地址有效性和容量上限等底线，并对身份、时点或可变性不同的检查分别判断——比如内容校验通过不代表后续不会发生 I/O 错误，后台计算完成也不代表接收方换代后该结果仍然有效。

如果发现文档缺少必要的契约说明，先找到事实负责方并补齐对应层次的声明；属于已知未完成实现时，链接到状态页。移除重复保护前，先确保原保护承担的责任已经在正确边界落实到位；如果候选保证实际上建立不起来，要么修好建立与维持机制，要么撤回这次简化。

## 数据与失败

`null`、空集合和零值各自应有唯一且明确的含义，不能同时用来表示“正常不存在”和“内部失败”。只读集合视图不保证其中的元素本身不可变；值对象只有在构造和修改入口都受控时，才能免除下游重复校验。

只在真正承担恢复、错误翻译、故障隔离或资源清理职责的位置捕获异常。遇到调用违约时，保留原始原因和触发者身份；“记录诊断日志”与“隔离故障后果”分开决定，遵守[产品失败边界](../product-decisions/decisions/failure-isolation.md)。资源清理严格按资源契约执行，是否允许重试则由接口约定的操作身份与幂等性条件决定。

## 代码契约

Seam 的类型定义、方法签名和声明注释本身，应当足以指导调用方写出正确的调用代码。实例共享的生命周期、不变量和架构关联写在类型注释上；具体方法只补充与公共规则不同的增量要求；字段只说明消费方确实需要依赖的约束。实现类内部则记录这些保证是如何建立和维持的，以及不显然的设计原因。

代码契约直接使用普通 Javadoc 编写：参数、返回值和异常用标准标签，其他维度按[声明格式](code-contracts.md#声明位置与格式)组织。签名和类型系统已经表达清楚的条件不必复述。架构契约与代码声明之间的对应关系见[契约映射](code-contracts.md#与架构契约的连接)。

### 源码注释的文档引用

源码注释中引用文档时统一写成 `[说明](docs/路径.md#章节)`，路径相对所属项目根目录，使用 `/` 分隔。引用 Java 符号使用 `{@link ...}`；Markdown 文档内部互链则相对当前文档解析。源码里的文档链接由 `docs/tools/check_docs.py` 统一检查，不依赖 Javadoc 自身的 HTML 链接解析。

```java
/**
 * <p>Seam: implements [lease ownership](docs/architecture/model-management/client-resources/overview.md#引用撤销与物理关闭).
 */
```

## Java 类型命名

用包名表达模块归属，用类型名表达具体职责。内部类型不加 `Ysm` 前缀，只在需要消除歧义时加上领域限定词（如 `MolangContext`、`ModelSoundId`）。接口与实现都按实际职责命名，不用 `I`、`Impl` 或 `Production` 这类机械后缀来区分。

常用后缀的语义约定如下：`State` 表示可变状态，`Binding` 表示绑定关系，`View` 表示访问视图，`Scope` 表示生命周期作用域，`Catalog` 表示目录；内建成员提供类命名为 `<Domain>Builtins`，有状态组件命名为 `<Domain>Component`，能力集合或资格描述命名为 `Capabilities`；事件处理器使用 `Handler`，事件载荷使用 `Event`。

`YsmExtension`、`YsmEventHandler`、`YsmEntityComponent` 保留 `Ysm` 前缀，以明确它们面向第三方模组接入；产品级入口和具体格式名也可以保留相应前缀。重命名 Java 类型不得改变 Molang 名称、资源 ID 或网络协议标识，同时必须同步更新生成源码、反射名称以及服务注册中的类名引用。

## 基建复用

现有门面能够满足职责时直接复用；如果只差少量能力，优先扩展原有门面。只有当职责定位、生命周期或性能约束明显不同、无法在原门面上合理扩展时，才新增独立机制，并说明引入后的维护成本。现有基础设施的选型和各领域入口见[基建指南](infrastructure.md)。

## 变更与验证

修改实现或契约时，应同步维护权威文档正文、保证的建立与维持代码，并沿着具体 seam 传播到消费方、组合契约以及上下游模块，直到不再影响职责边界为止。传播复核时特别要检查输入入口、异步投递、回调、扩展接入、旁路构造和拒收路径；修改共同规则时，要覆盖所有显式继承它的契约。

一旦需求或共享设计发生变化，需要回过头复核所有受影响的任务、实现代码和验证证据（包括已经完成的部分）；前提未变且仍然成立的结论可以直接沿用。

如果只是细化局部调用要求且不改变对外架构保证，只需更新代码声明、实现和调用方。但如果收紧了前置条件，或者改变了失败语义与资源释放后果，就必须退回[设计指南](design.md#交付与变更)重新评估架构契约。

拆分、合并或迁移契约时，要完整保留原有义务、例外和理由，修正引用处的语义说明，并删掉重复正文。涉及跨边界交接、发布资格、资源释放和跨模块依赖的内容，应放到可精确引用的语义小节中；引用方要写明自己依赖了什么前提，同时尽量保持未变语义的小节标题稳定。

验证时根据改动的影响面，挑选最可能击穿契约保证的入口或并发竞态，运行最小相关验证集合：优先复用已经覆盖该契约的测试，只有存在明确证据缺口时才补充新测试。测试替身只能通过显式架构 Seam 注入，不得为了单测向生产类添加多参数测试专构、生产零实现的故障注入 `Hook` 或白盒计数方法。相关检查全部通过后，除非又做了新改动、出现失败或仍有未解疑点，否则不必反复扩大或重跑测试——当然，这不免除已经规定的集成验证和独立审查。已有证据且前提未变时可以直接沿用；投入尺度、分层边界与测试维护规范遵循[验证边界](../verification/policy.md)，同时同步维护验证入口与状态页里的已知差异。

交付结果时应简明列出实际改动、关键取舍理由、执行过的验证命令与结果、未完成项以及已知限制，让审查者无需重演整个实现过程就能判断质量。
