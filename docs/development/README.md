# 开发指南

本目录按开发阶段组织指南。[设计指南](design.md)与[实现指南](implementation.md)分别负责设计总则和实现总则，专题文档只展开需要独立查阅的细节；具体的产品、标准与子系统契约以各自正文为准。

## 理解代码与设计

理解代码和设计时，以现有文档为主、源码检索为辅。先从[文档入口](../README.md)定位产品契约、架构边界和复杂度子图，形成判断与具体的待核验问题，不要无条件遍历源码或做全仓索引。

源码检索用于核实影响结论的缺口、排查文档与行为的冲突、理清职责替代关系，以及支持实际修改和验收。顺着已发现的依赖定向查询，拿到足够证据就停下来。文档不能替代当前源码与运行验证，当前实现也不能反过来改写产品契约。

## 开发步骤

如果已有结论的依据和前提没有变化，可以直接沿用，只处理本次变更波及的部分，不要求每个阶段都新建一份文档。

1. **明确需求与决定**：弄清要解决的问题、受影响用户和预期结果，从[产品决策](../product-decisions/README.md)核对上游依据。一旦出现产品语义冲突，交由维护者确认。
2. **明确契约**：从[架构入口](../architecture/README.md)找到涉及的 seam，按[设计指南](design.md#契约与责任)明确职责边界、结果保证、失败语义和资源义务；涉及格式或协议时查阅[标准](../standards/README.md)。
3. **选择设计**：按[设计指南](design.md)权衡方案与长期维护成本；涉及跨模块协调机制时，先查阅[复杂度地图](../complexity-map/README.md)。
4. **实现与验证**：按[实现指南](implementation.md)落实并维持各项保证，同步维护代码声明、实现及受影响的调用方，然后运行最小范围的相关验证。
5. **审查**：按[分层审查](review.md)逐层核对需求、决定、契约、设计与代码，明确列出验证结论和尚未覆盖的范围。

三层契约各有分工：产品行为契约规定对外承诺，seam 契约划定跨子系统的责任交接，代码契约细化具体调用和访问要求。各类文档的阅读与维护遵循对应入口的规则。

### AI Coding 协作建议

建议按开发阶段切分会话，用任务文档在阶段之间传递结论；你也可以按个人习惯封装成本地 skill：

1. 在同一个会话内分两个阶段完成决策和契约。
2. 开新会话，分两个阶段完成设计和实现。设计阶段可按需拆分子任务并制定公共约束；如果子任务超过 1 个，建议为每个子任务开独立会话。
3. 再开一个独立会话完成审查和验收。

每个会话不得擅自修改任务文档里不属于当前阶段的内容。如果发现上一阶段的结论需要调整，应交由用户或上层 agent 拍板，并退回对应的上一阶段会话处理。

### 动画与渲染热路径

涉及动画更新或图形渲染热路径的开发任务，性能与正确性同等重要，且不能以牺牲可维护性为代价。必要时可以在局部放宽非关键的正确性要求以换取性能，但必须明确写出取舍范围、性能依据与行为影响；产品承诺和核心边界契约不得据此擅自放宽。

这类任务通常需要人直接参与设计、权衡取舍、调整实现和最终验收，不能假定 AI 可以独自完成这些判断。AI 应提供可审查的方案与实测证据；涉及正确性取舍时，必须由人确认边界，并最终验收性能、正确性与可维护性。
