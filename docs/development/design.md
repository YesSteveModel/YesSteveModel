# 设计指南

本页约定设计阶段的项目专属准则，覆盖边界契约、Java 资源/执行模型与常见架构模式。落地细节见[实现指南](implementation.md)，验收口径见[分层审查](review.md)。

## 从结果选择机制

- **整体合理性优先**：与当前问题紧密相关的旧设计与代码默认不视为兼容基线，不要为了凑“最小改动”而保留不合理结构。兼容义务只来自[产品决策](../product-decisions/README.md)、已冻结标准或明确需求。
- **控制状态与协调成本**：在满足契约的方案中，优先选择长期状态更少、恢复分支更简单、状态空间有界且必然终止的机制。新增或调整复杂跨模块协调前，先查[复杂度地图](../complexity-map/README.md)。
- **避免无收益包装**：仅在需要明确所有权、生命周期、访问权限或独立演化边界时缩窄接口；不要为了防内部受控调用方而包纯转发包装类。

## 契约与责任

只对 **seam**（子系统或独立子模块之间交接职责、由权威方裁决状态或产出可独立消费结果的边界）显式声明契约；内部不变量靠类型与封装维持。

- **归属**：全局不变量归系统入口或组合方；单个 seam 归提供方。共享同一生命周期的 `acquire`/`poll`/`cancel`/`close` 放同一契约；准入、失败或寿命独立时拆分。
- **共同规则**：仅抽取多份契约真正共享且非显然的约束并写明适用范围；需要为必需默认资源（required default）显式留出例外。
- **方向一致**：实现不得比接口契约更苛刻地收紧前置条件或扩大失败面；若局部需求导致合法用法失效，应重评边界而非硬补限制。

### 架构契约格式

每份 seam 契约从以下六个有序字段中按需选取（至少一项，保持相对顺序），无非显然增量信息的字段直接省略：

| 字段 | 内容 |
|---|---|
| 边界与权威 | 提供方、消费方、输入输出范围，以及规范来源与运行时决定者 |
| 前置条件与输入 | 调用方须满足的非显然前提、身份要求与当前依赖的调用窗口 |
| 结果与保证 | 建立方、维持方、可见时点与覆盖范围 |
| 所有权与时序 | 保留与关闭责任、借用边界、并发假设、必要先后顺序及失效事件 |
| 失败与拒收 | 非显然的失败分类、过期/拒收语义及未交付资源处理责任 |
| 证据与依赖 | 上游依赖、实现与验证入口、已知差异与覆盖范围 |

书写时严格区分两类约束语气：
- **外部硬约束**（产品决策、已冻结标准、宿主行为与内存安全底线）：直接说明不可违背的条件与后果。
- **当前实现前提**（内部模块划分、共享可变状态、串行假设、帧内读写窗口等）：用中性事实语气描述现状与重构时需同步调整的依赖，不写成永久禁令。

目录组织见[架构文档维护](../architecture/documentation-rules.md#契约页面组织)，代码级声明见[代码契约](code-contracts.md)。

## 权威、所有权与提交

- **单权威与单 owner**：一份权威事实只有一个运行时 authority；派生视图与缓存不回写权威。区分四个时点：权威决策、通知发出、资源就绪、消费方安装生效。
- **逻辑撤销与物理释放解耦**：撤销一份引用不会关闭仍被其他方保活的共享资源；所有权转移须写明成功点与失败后的回收责任。
- **零重叠退役顺序**：当重建或重入要求新旧工作零重叠时，按“封口拒绝新请求 → 等待在途工作与外部承诺全部退出 → 清理状态”收尾，不能以超时或队列瞬时为空代替退役证明。
- **有界池与防死锁**：有限容量 worker 池等待网络、owner 线程或同池任务时，须证明容量独立、无环且取消可唤醒，否则先等外部依赖完成再入池。
- **失败处置**：优先在最小边界内显式拒绝或纳入既有生命周期收尾，遵守[产品失败边界](../product-decisions/decisions/failure-isolation.md)；不把暂态失败锁死为永久结果，不为极低概率边界随意引入长期恢复状态。

### Java 资源选择

- **默认选 `Cleaner`**：当资源压力可反映到 GC 内存占用且延迟释放不影响正确性时，用 `Cleaner` 省去跨消费方的关闭协调。
- **必须显式关闭**：当 GC 感知不到压力或正确性要求及时释放时——如锁、文件句柄、profiler scope、GPU 资源、决定网络传输取消时机的 lease。
- 固定作用域临时 buffer 用 `BufferStorage`，多资源构造回滚用 `ResourceTransaction` / `ScopeGuard`，入口见[基建指南](infrastructure.md#生命周期与构造回滚)。

### Java 执行边界

- 每个 `Executor` 归属明确的领域 owner，自管容量/背压、取消、迟到结果与关闭顺序；**项目不设通用异步 runtime**，也不用公共池替代领域生命周期。
- 必须在 Minecraft client、render 或 server 线程执行的工作，一律使用宿主提供的调度入口。现有执行入口见[基建指南](infrastructure.md#并发与执行边界)。

### 用 lease 与轮询简化资源取得链

在“已有 owner tick 驱动、消费方随时可能提前退出”的跨子系统资源获取链路中，优先采用 **申请即得独立 lease + owner 定期轮询就绪**，替代消费方侧多层嵌套的 `Future` 回调与迟到回收协议（提供方内部计算/去重仍可用 `Future`）：

- lease 状态从 Pending 单向推进到 Ready；稳定状态下 tick 只观察，不重申请求、不增引用计数；消费方退出后由提供方独立收尾在途工作。
- Ready 只代表资源本身就绪，消费方仍须按当前模型身份、权限与安装窗口决定是否采纳；本地轮询不能替代跨网络的 revision/过期检查。
- 交接时先让接收方拿到独立使用权，再退出原 lease；关闭 lease 只撤销本份使用权，后台任务彻底退出后才归还输入资源与并发配额。
- 轮询复用 owner 既有 tick 且每次扫描有界；关闭路径不依赖已停掉的普通 tick。
- 测试覆盖：永久停 poll、Pending/Ready 阶段退出、目标替换后迟到结果与交接失败。

## 交付与变更

入口路径、交付结果、权威归属、所有权转移、并发窗口、失效条件或失败语义变更时，须同步更新对应架构契约；修改共同规则须复核所有显式依赖方。仅变更局部实现而不影响对外契约时，只更新实现映射或源码即可。变更传播与验证见[实现指南](implementation.md#变更与验证)。
