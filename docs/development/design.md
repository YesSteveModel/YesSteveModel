# 设计指南

本页定义设计总则，负责需求到契约、责任与机制的选择。产品、标准和子系统正文拥有实际契约；[实现指南](implementation.md)负责兑现保证，[分层审查](review.md)负责检查结果。

## 从结果选择机制

确认真实问题、受影响用户、可验证结果及适用约束，从[产品决策](../product-decisions/README.md)定位依据。已有结论的前提未变时直接继承；条件变化、缺口或反证只触发受影响部分的复核。产品含义冲突交由人裁决。

区分明确需求、已验证事实和假设。影响方向或返工成本较高的假设，先用定向证据或小型原型验证。

在满足契约的方案中比较整体成本：可达状态、ownership、生命周期交错、跨域协调、恢复、可观测性和迁移。默认选择长期状态和恢复分支更少的机制；有界且可终止的显式状态可以排除更大的隐式状态空间。代码量、机制数量或最小 diff 不代替设计判断，复杂度转移也不算收益。

设计以整体合理性为目标。任务边界之外但与问题紧密相关的设计和代码，默认不作为必须保持和兼容的基线；不因追求最小实现而保留不合理设计。

机制与扩展能力以当前需求为依据，抽象承载真实契约或独立变化原因。复用应匹配语义、ownership、失败、生命周期和部署约束；兼容义务来自产品依据或明确需求。新增或调整协调机制前，查阅[复杂度地图](../complexity-map/README.md)。

限制接口能力应承载所有权、生命周期、权限、不变量或独立演化责任，并说明现有类型与调用契约为何不足。仅为防止受控内部调用者违反既定契约，默认不新增纯转发包装。

设计结论应说明保护的结果、责任方、资源终态和失败后果。验收明确代表性场景、预期结果和判定依据；预期结果来自需求与契约，判定独立于候选实现。局部算法按实际需要分析。

## 契约与责任

### 适用范围

只要求 seam 显式声明契约。Seam 是子系统之间的责任交接、事实裁决或可独立消费结果的边界，递归拆分后的子系统同样适用。目录、可见性、代码量和并发本身不构成 seam；内部不变量优先由类型、封装和实现维持，必要时用短注释说明。

架构契约定义跨边界责任与保证，代码契约细化调用和访问义务。契约只覆盖消费者需要依赖的语义：保证的对象、前提、有效窗口、失效条件和失败后果。可替换算法归实现；锁和线程要求仅在调用者承担义务时进入契约。

### 划分与继承

系统不变量归系统入口或实际组合责任方；seam 契约归提供方，跨域组合保证归组合责任方。一个子系统可以提供多个 seam；同一生命周期的 acquire、poll、cancel、close 通常属于同一契约。输入资格、交付保证、失败裁决或生命周期独立时，分别定义。

共同规则只保存共享义务，明确适用范围；消费者精确引用继承条款。目录、父子页面和同类不建立隐式继承。每项契约应通过自身正文和显式依赖提供完整义务，不依赖无关同级契约。前提或例外不一致时重新划分共同规则，普通失败规则保留 required default 的例外。

实现不能加强接口前置条件、削弱结果保证或扩大允许失败。局部调用义务使架构允许的使用无法成立时，应重评边界。

### 架构契约格式

每项 seam 按以下六字段组织，字段可精确引用共同条款，并说明继承责任。

| 字段 | 内容 |
|---|---|
| 边界与权威 | Provider、consumer、输入输出范围；规范来源与运行时裁决者 |
| 前置条件与输入 | 调用方建立的条件、继承的保证、身份和进入窗口 |
| 结果与保证 | 建立者、维持者、可见时点和保证范围 |
| 所有权与时序 | 保留与关闭责任、借用、并发、必要偏序和失效事件 |
| 失败与拒收 | 允许失败、过期、违约和拒收；隔离、降级、重试及未交付资源责任 |
| 证据与依赖 | 精确上游契约、落实与验证入口、已知差异和证据范围 |

本级应解释可消费的义务和组合责任；没有资源转移、长期状态或自动重试时，说明实际边界。理由紧邻义务，不在设计取舍中另设隐含前置条件。证据字段链接现有证据及 status 差异。

页面组织见[架构文档维护](../architecture/documentation-rules.md#契约页面组织)，声明格式见[代码契约](code-contracts.md)。

## 权威、所有权与提交

一个事实只有一个 authority，一个生命周期只有一个 owner。快照、投影和缓存消费权威事实；规范来源决定承诺，运行时 authority 裁决某次事实。组合方承担局部保证未覆盖的责任。

已接纳工作和外部 commitment 应到达终态。所有权转移明确成功条件及失败后责任；逻辑责任与物理回收分别闭合。撤销引用不关闭仍被保留的共享资源，显式关闭应有固定责任方和结束条件。

提交只在最小可观察范围原子化。区分权威决定、通知传播、资源可用和实际消费；异步接纳、计算完成、发布与安装分别定义。状态查询应说明是快照还是持续有效的使用资格；操作与失效由 owner 排序，或在排除失效的窗口执行。单次调用线程安全不保证组合操作原子性。

### Java 资源选择

资源管理默认使用 Cleaner；资源压力能由 GC 的内存信号反映，且释放延迟不影响正确性时，允许物理回收滞后。GC 无法感知容量或正确性要求及时终结的资源使用显式关闭，例如锁、文件句柄、profiler scope、GPU 资源及影响传输会话取消的 lease。

固定作用域的 buffer 使用 [Storage](infrastructure.md#buffer-与所有权)。回收与构造回滚入口见[基建指南](infrastructure.md#生命周期与构造回滚)。

## 执行、退役与失败

有限容量应显式表达外部进展依赖。稀缺 worker 等待传输、owner 线程或同容量工作时，应证明容量独立、依赖无环及取消可唤醒，或先终结依赖再接纳工作。取消请求不结束借用或资源占用，义务在约定终点结束。

退役以旧工作不再产生可见副作用为准。要求重新进入时零重叠的契约，应先封口，再终止所拥有的工作和 commitment，最后处置数据；超时或队列暂时为空不能证明退役。

失败保留原因、身份及责任边界，优先借现有生命周期收敛。暂态失败不冻结为永久结果，不确定结果不猜测性部分应用。对稳定性及最终结果影响不大的不确定性留在局部，避免为此增加长期状态或全局协调。

低概率且无法安全消歧时，默认在最小所属边界显式拒绝或硬失败。只有该处置会破坏核心日常用例、造成不可接受的数据丢失，或把普通输入升级为 startup 级故障时，才考虑增加机制；新增仍须证明风险收敛收益超过长期状态、恢复和验证成本。处置遵守[产品失败边界](../product-decisions/decisions/failure-isolation.md)和局部隔离义务；资源归还独立于恢复责任。

接口应区分正常否定结果、运行失败和违约，明确通道、提交状态及资源后果。同步抛出和异步完成分别定义，同一失败只交付一次。重试资格取决于身份、幂等性和重复副作用；`Error` 与进程级故障继承上层隔离边界。

### Java 执行边界

Executor 归具体领域 owner，明确容量或背压、取消、迟到结果和 shutdown 顺序。Minecraft client/render/server thread 的工作使用宿主调度入口。项目没有供所有业务共享的通用异步 runtime，已有线程池不能替代领域生命周期。

可恢复并发失败由领域 owner 形成 typed result、diagnostic 或 terminal state。共享抽象应保留各领域的取消和发布语义；现有入口及限制见[基建指南](infrastructure.md#并发与执行边界)。

## 交付与变更

设计交付受影响的契约、机制选择、理由与验证入口。新增子系统同时建立契约入口和上级导航；新增 seam 接入所属入口。代码声明按[实现指南](implementation.md#代码契约)细化。

进入路径、交付结果、权威、资源转移、并发窗口、失效条件或失败语义变化时，同步更新架构契约。共同规则变化时复核显式继承者；局部实现变化且契约不变时，维护实现即可。变更传播和验收见[实现指南](implementation.md#变更与验证)。
