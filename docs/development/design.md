# 设计指南

本页规定设计阶段的总则，说明如何从需求出发确定边界契约、分配职责并挑选合适的技术方案。具体的业务承诺与接口契约以产品、标准和各子系统正文为准；落地细节见[实现指南](implementation.md)，验收口径见[分层审查](review.md)。

## 从结果选择机制

动手设计之前，先确认要解决的真实问题、受影响用户、可验证的目标结果以及适用约束，并从[产品决策](../product-decisions/README.md)查明上游依据。已有结论的前提没有变化时直接沿用；只有条件变化、发现缺口或出现反证时，才复核受影响的部分。涉及产品语义冲突时，交由维护者确认。

明确区分已经敲定的需求、已经核实的事实，以及尚未验证的假设。对方向影响大或返工代价高的假设，先通过定向核查或小型原型验证，再铺开设计。

在都能满足契约的候选方案之间，应从整体长期成本出发做取舍，重点比较状态空间大小、资源所有权、生命周期交错、跨模块协调、错误恢复、可观测性与后续迁移成本。默认优先选择长期状态更少、恢复分支更简单的方案；用有界且必然终止的显式状态，往往比放任隐式状态膨胀更容易维护。代码行数少、机制数量少或 diff 最小都不能代替设计判断，把复杂度从一个模块甩给另一个模块也不是真正的简化。

设计以系统整体合理性为目标。与当前问题紧密相关的周边设计与旧代码，默认不视为不可触碰的兼容基线；不要为了凑出“最小改动”而保留明显不合理的结构。

新增机制或扩展能力必须由当前需求驱动，抽象也应对应真实的跨边界契约或独立的变化原因。复用现有组件时，要确认语义、所有权、失败处理、生命周期和部署约束确实匹配；兼容义务只来自产品决策或明确需求。新增或调整跨模块协调机制前，先查阅[复杂度地图](../complexity-map/README.md)。

刻意缩窄一个接口的能力时，应当是为了明确所有权、生命周期、访问权限、内部不变量或独立演化边界，并说明现有类型和调用契约为什么不够用。如果只是为了防止受控的内部调用方违反既定契约，默认不要额外包一层纯转发包装类。

设计结论要交代清楚：最终保护了什么结果、由谁负责、资源如何释放以及失败后会怎样。验收标准应列出代表性场景、预期结果和判定依据；预期结果来自需求和契约，判定方式不能照搬候选实现自身的逻辑。局部算法细节按实际需要分析即可。

## 契约与责任

### 适用范围

只要求在 seam（跨边界接缝）处显式声明契约。所谓 seam，是指子系统之间交接职责、由权威方给出状态结论，或产出可独立消费结果的边界；子系统内部进一步拆分出的子模块同理。仅仅因为分了目录、是 `public`、代码量大或涉及并发，并不构成 seam；模块内部的不变量优先靠类型系统、封装和实现来维持，必要时补简短注释即可。

架构契约规定跨边界的职责划分与总体保证，代码契约进一步细化方法调用与数据访问要求。契约只写消费方必须依赖的语义——保证什么对象、需要什么前提、在什么窗口内有效、什么事件会使其失效，以及失败后有什么后果。可自由替换的内部算法留在实现层；锁策略和线程要求只有在需要调用方配合时才写入契约。

### 划分与继承

全局性的系统不变量归系统入口或实际负责组合的模块；单个 seam 的契约归提供方；跨多个模块组合而成的保证归组合方。一个子系统可以对外提供多个 seam：共享同一生命周期的 `acquire`、`poll`、`cancel`、`close` 通常写在同一份契约里；如果输入准入、交付保证、失败处理或生命周期各自独立，则分开定义。

共同规则只放多份契约真正共享的要求，并写明适用范围；具体契约需要显式引用它所继承的条款，不要依靠目录位置、父子页面或同级排版形成隐式继承。每份契约自身加上显式引用的依赖，就应当完整说明全部义务，不要让读者去无关的同级契约里拼凑前提。一旦某条共同规则的前提或例外不再一致，就应当重新划分；普通的失败规则要为必需默认资源（required default）留出明确例外。

实现不能比接口契约更苛刻地收紧前置条件、削弱结果保证或扩大允许失败的范围。如果某个局部调用要求导致架构允许的合法用法无法成立，就应回过头重新评估边界，而不是硬补限制。

### 架构契约格式

每份 seam 契约按以下六个字段组织；字段内可以精确引用共同规则条款，并写清本级继承的责任：

| 字段 | 内容 |
|---|---|
| 边界与权威 | 提供方、消费方、输入输出范围，以及规范来源与运行时决定者 |
| 前置条件与输入 | 调用方需要满足的条件、继承的保证、所需身份和允许调用的窗口 |
| 结果与保证 | 由谁建立、由谁维持、从何时起可见以及保证覆盖的范围 |
| 所有权与时序 | 保留与关闭责任、借用边界、并发规则、必要先后顺序及失效事件 |
| 失败与拒收 | 允许的失败类型、过期、违约和拒收语义，以及隔离、降级、重试与未交付资源的处理责任 |
| 证据与依赖 | 精确的上游契约、实现与验证入口、已知差异和现有证据的覆盖范围 |

每一级文档都应说清本层实际承担的义务和组合责任；如果不存在资源所有权转移、长期状态或自动重试，直接写明即可。设计理由紧跟在对应义务旁边，不要把隐含的前置条件藏到后面的“设计取舍”章节里。证据字段直接链接现有验证入口以及状态页里记录的已知差异。

契约页面的目录组织见[架构文档维护](../architecture/documentation-rules.md#契约页面组织)，代码层面的声明格式见[代码契约](code-contracts.md)。

## 权威、所有权与提交

同一份权威事实只能有一个 authority（权威来源），同一段资源生命周期只能有一个 owner（负责方）。快照、派生视图和缓存只能消费权威事实，不能反过来篡改权威；规范文档决定产品承诺，运行时 authority 决定某一次具体请求的结果。各局部保证之间没覆盖到的衔接空隙，由组合方兜底负责。

已经接纳的工作和对外做出的承诺（commitment）都必须走到明确的终点。涉及所有权转移时，必须写清何时算转移成功，以及转移失败后由谁回收。逻辑上的引用撤销和底层的物理资源释放是两件事，各自收尾、互不混淆：撤销一份引用不会关闭仍被其他方保活的共享资源，而需要显式关闭的资源必须有固定的负责方和清晰的关闭时机。

原子提交只做在最小可观察范围内，不要随意扩大锁或事务边界。同时要注意区分几个不同的时点：权威做出决定、通知发出去、资源准备就绪、消费方实际用上——异步接纳、计算完成、对外发布和安装生效也应各自定义清楚。状态查询接口必须写明返回值是“瞬间快照”还是“持续有效的使用资格”；普通操作与失效事件的先后顺序应由 owner 统一排序，或在已排除失效的窗口内执行。单个方法线程安全，不等于多个调用组合起来也是原子的。

### Java 资源选择

Java 侧资源回收默认优先使用 `Cleaner`。只要资源压力能反映在 GC 的内存占用上，且稍微延迟释放不影响程序正确性，就允许物理回收滞后，借此省去跨消费方的关闭协调。相反，如果 GC 感知不到这类资源的容量压力，或者正确性要求必须及时释放——例如锁、文件句柄、profiler scope、GPU 资源，以及决定网络传输能否及时取消的 lease——则必须显式关闭。

固定作用域内的临时 buffer 使用 [Storage](infrastructure.md#buffer-与所有权)。回收工具与构造失败回滚入口见[基建指南](infrastructure.md#生命周期与构造回滚)。

## 执行、退役与失败

有界线程池或有限容量队列如果会阻塞等待外部进展，必须把这条依赖关系写明。当稀缺的 worker 线程需要等待网络传输、owner 线程或同一池内的其他工作时，必须证明两边容量相互独立、依赖无环且取消能及时唤醒等待；否则就应该先等依赖结束，再把任务接纳进有限池。另外，发起取消请求不等于立刻结束借用或释放资源，相关义务要等到约定的终止点才算结束。

组件或会话退役（retirement）的标准，是旧工作再也不会产生任何可见副作用。如果契约要求“重入或重建时新旧工作零重叠”，必须按固定顺序执行：先封口拒绝新请求，再等当前拥有的工作和外部承诺全部结束，最后清理数据。仅仅等了一段超时，或者看到队列暂时为空，都不能证明旧工作已经彻底退役。

处理失败时要保留失败原因、相关身份和责任边界，优先纳入现有生命周期流程收尾，而不是另加一套并行状态。暂态失败不能直接锁死成永久结果，状态不明的操作也不能凭猜测做部分应用。对稳定性和最终结果影响微小的局部不确定性，就地消化即可，不要为了追求完美而引入长期状态或全局协调。

遇到发生概率很低、又无法安全消歧的异常边界时，默认在最小所属边界内显式拒绝或硬失败。只有当这种做法会破坏核心日常场景、导致不可接受的数据丢失，或把普通输入问题放大成启动期故障时，才考虑引入额外恢复机制；而且必须证明降低风险带来的收益高于新增长期状态、恢复逻辑与测试验证的成本。失败处置遵循[产品失败边界](../product-decisions/decisions/failure-isolation.md)和各模块自身的隔离义务；无论由谁负责恢复，已占用资源的归还责任都不能含糊。

接口必须把三类情况分开定义：正常的否定结果（例如未找到、已过期）、运行时失败（例如 I/O 错误）和调用违约。每类都要写清报告通道、状态是否已提交以及资源怎么处理；同步抛异常和异步完成失败分开约定，同一次失败只交付一次。能不能重试取决于操作身份、幂等性以及重复执行的副作用；`Error` 与进程级故障沿用上层隔离边界。

### Java 执行边界

每个 `Executor` 都归属具体的领域 owner，由它明确容量或背压策略、取消行为、迟到结果处理以及关闭顺序。必须在 Minecraft client、render 或 server 线程执行的工作，一律使用宿主提供的调度入口。项目不设供所有业务共用的通用异步 runtime，也不能拿现成的公共线程池替代领域自身的生命周期管理。

可恢复的并发失败由所属领域 owner 转为明确的结果类型、诊断信息或终止状态。如果多个领域复用了同一套底层抽象，抽象本身必须保留各自原本的取消与发布语义；现有执行入口及限制见[基建指南](infrastructure.md#并发与执行边界)。

### 用 lease 与轮询简化资源取得链

对于“已有 owner tick 驱动、且消费方可能随时提前退出”的跨子系统资源获取链路，优先采用“申请即拿到独立 lease，再由 owner 定期轮询是否就绪”的模式，用来替代消费方一侧层层嵌套的 `Future` 回调、结果接管和迟到回收协议。注意，提供方内部用于执行实际计算、I/O 或共享去重工作的 `Future` 可以保留；是否采用 lease + 轮询取决于职责划分与生命周期特征，而不是单纯看 `Future` 嵌套了几层。

采用这种模式时遵守以下约定：

- 同一个 lease 的状态从 Pending 单向推进到 Ready；稳定状态下 tick 只观察状态，不重复发起申请，也不增加引用计数。消费方提前退出后，由提供方独立收尾在途工作和无人认领的结果。
- Ready 只证明资源本身已满足契约保证。消费方仍须结合当前的模型身份、权限和安装窗口决定是否采用；“当前实际在用什么”应直接由真实安装结果决定，而不是另存一份状态副本。此外，本地轮询不能替代跨网络操作所需的 revision 或过期检查。
- 交接时先让接收方拿到独立的使用权，再让来源方退出。关闭 lease 只撤销本份使用权；实际后台工作彻底退出后，才归还它占用的输入资源和并发配额。
- 轮询复用所属 owner 原有的推进 tick，且每次扫描范围有界。关闭路径不能依赖已经停掉的普通 tick，也不能要求已经退出的消费方继续 poll；跨线程发布与关闭的先后顺序按对应契约约定执行。
- 测试需要覆盖永久停止 poll、在 Pending 或 Ready 阶段退出、目标被替换后收到迟到结果，以及交接失败等边界。评估这项简化时，把省掉的交接状态、扫描与分配开销、以及从就绪到被采用的延迟分开衡量，不要默认宣称它一定更快。

## 交付与变更

设计阶段的交付物包括：受影响的契约、最终选定的机制、选择理由以及验证入口。新增子系统时要同步建立契约入口和上级导航链接；新增 seam 时要接入所属子系统的契约入口。代码层面的声明按[实现指南](implementation.md#代码契约)细化。

一旦入口路径、交付结果、权威归属、资源所有权转移、并发窗口、失效条件或失败语义发生变化，必须同步更新架构契约。修改共同规则时，要逐一复核所有显式继承它的契约；如果只改了局部实现而对外契约不变，只需维护实现文档或源码即可。变更传播和验收流程见[实现指南](implementation.md#变更与验证)。
