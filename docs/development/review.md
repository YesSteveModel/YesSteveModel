# 分层审查

审查开始前，先明确各个受影响仓库的比较基线，把本次完整变更及受影响的依赖全部纳入范围——包括已提交、已暂存、未暂存以及未跟踪的文件。测试通过只证明被测代码符合测试预期，不能替代对需求、产品决定或边界契约的审查。

| 层级 | 检查重点 |
|---|---|
| 需求与决定 | 是否解决了真实问题，是否符合产品决定及其适用边界，选择理由与代价是否站得住脚 |
| 契约 | 各项保证是否有上游依据，职责划分是否闭环无遗漏，产品、架构与代码三层契约是否一致 |
| 设计 | 所选机制是否真正履行了契约，是否重复引入了多余的状态副本、权威判断点、生命周期、同步锁或恢复流程 |
| 代码与验证 | 实现与调用方是否遵守契约，失败路径和资源释放是否正确，已有验证证据是否足以支撑结论 |

如果缺少某一层必需的上游依据，应直接标明该层无法审查，不要从实现代码或测试用例反推需求。同样，验证结论只代表实际检查过的范围，不能外推。

## 防御机制

防御性代码不是越多越稳妥。审查中遇到额外的封装、状态二次确认、参数或返回值检查、锁、防御性拷贝、fallback、重试、恢复状态，以及 revision 或 epoch 校验时，都应要求说明它们究竟在兜底哪一项上游保证尚未覆盖的独立风险；具体核对项见[保护责任](implementation.md#使用保证与保护责任)。

对上游已经建立且在当前窗口内持续有效的内部保证，代码应直接信任，不必层层重查。但反过来，准备删掉某项保护前，必须先确认原职责已经有明确边界接管——纸面上的契约声明不能替代真正需要的线程同步、内存安全检查和故障隔离。

## 问题回退

审查提出的每个问题都要交代清楚：依据来自哪里、预期行为与实际行为有什么差异、影响范围有多大、当前证据覆盖到哪里，以及应该由哪一方负责处理。按问题性质退回对应阶段：涉及产品语义冲突的交由维护者拍板，契约缺口退回契约负责方，结构性问题退回设计阶段，普通实现错误退回实现阶段。

当预期行为明确且缺陷已经确认时，可以补充确定性的复现测试来辅助定位；复现测试只应表达已有契约，不要顺手发明新需求。

最终验收结论分为三类：**通过**、**需修改**、**证据不足**。只有验收目标与上述四层审查全部通过，才能判定为通过；报告中应把已确认的问题和尚未验证覆盖的范围分开列明。
