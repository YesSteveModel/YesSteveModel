# 分层审查

审查须纳入受影响仓库的完整变更（已提交、已暂存、未暂存与未跟踪文件），按四层自上而下核对：

| 层级 | 检查重点 |
|---|---|
| 需求与决定 | 是否符合产品决策及适用边界，取舍理由与代价是否成立 |
| 契约 | 保证是否有上游依据，职责划分是否闭环，产品/架构/代码三层契约是否一致 |
| 设计 | 机制是否真正履行契约，有无多余的状态副本、重复权威点、冗余锁或恢复分支 |
| 代码与验证 | 实现与调用方是否守约，失败与释放路径是否正确，验证证据是否覆盖关键风险 |

缺少必需上游依据时直接标明该层无法审查，不从实现或测试反推需求。

## 防御机制审查

遇到额外包装、二次状态确认、参数重查、外层锁、防御拷贝、fallback、重试或 revision 校验时，要求说明其兜底的独立上游缺口（见[保护责任](implementation.md#使用保证与保护责任)）。删减保护前须确认原职责已有明确边界接管。

## 回退与结论

每个问题需指明依据、预期与实际差异、影响范围及归属层（产品冲突交维护者，契约/结构/实现问题退回对应阶段）。

最终结论仅三类：**通过**、**需修改**、**证据不足**；结论中分别列出已确认问题与未验证覆盖范围。
