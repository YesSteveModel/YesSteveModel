# 分层审查

明确各仓库的比较基线，覆盖本次完整变更及受影响的依赖，包括已提交、暂存、未暂存和未跟踪的改动。测试通过不能替代需求、决定或契约的审查。

| 层级 | 检查重点 |
|---|---|
| 需求与决定 | 是否解决真实问题，符合产品决定及其适用边界；理由和代价是否成立 |
| 契约 | 保证是否有依据，责任是否完整，产品、架构和代码契约是否一致 |
| 设计 | 机制是否履行契约，是否重复引入状态、裁决者、生命周期、同步或恢复 |
| 代码与验证 | 实现和调用是否符合契约，失败与资源终态是否正确，证据是否支持结论 |

缺少必要依据时，标明对应层级无法审查，不从实现或测试反推需求。验证结论只覆盖实际检查的范围。

## 防御机制

封装、状态确认、参数/返回值检查、锁、拷贝、fallback、重试、恢复状态、revision/epoch 等防御性设计和代码应能指出上游保证尚未覆盖的独立责任。按[保护责任](implementation.md#使用保证与保护责任)核对具体机制。

直接信任已建立且持续有效的内部保证。删除保护前应确认责任已有覆盖；契约声明不能代替必要同步、内存安全和失败隔离。

## 问题回退

每个问题说明依据、预期与实际、影响、证据边界和责任方。产品含义冲突交由人裁决，契约缺口返回契约责任方，结构性问题返回设计，普通缺陷返回实现。

预期明确且缺陷已确认时，可用确定性复现帮助定位；复现测试只表达已有契约。

验收结论区分通过、需修改和证据不足。验收目标与各层审查均通过才判定通过；已确认问题和未证明范围分别列明。
